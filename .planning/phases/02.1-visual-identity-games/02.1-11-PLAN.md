## What this planning session already ruled out (do not repeat this investigation)

A headless-LVGL diagnostic was built during planning to root-cause this bug before writing the
task below, using the ALREADY-COMPILED object files from a `pio run -e native_sim` build
(`.pio/build/native_sim/src/ratimos/apps/castelo_app.o`, `app_shell.o`, `status_bar.o`,
`theme.o`, `icons.o`, `progress_images.o`, `progression.o`) linked against `liblvgl.a` with a
manually-created headless `lv_display_t` (a raw `uint8_t` RGB565 buffer via
`lv_display_set_buffers(..., LV_DISPLAY_RENDER_MODE_FULL)`, no SDL/window needed) and a
minimal stub for `ratimos_storage_get_progression()` returning `shared_completions = 1`
(matching the UAT session, which had already won one conexo round before reaching the castelo
screen).

Calling the REAL, unmodified `ratimos_castelo_show(NULL)` entry point in that harness and then
sampling the decoded framebuffer at the stage image's coordinates (via `lv_obj_get_coords()` --
**not** `lv_obj_get_x()`/`lv_obj_get_y()`, which return parent-relative offsets, not absolute
screen coordinates; this distinction caused one false-positive "repro" during this
investigation that a coordinate fix immediately resolved) showed the stage image rendering
CORRECTLY: three distinct RGB565 color values present in the expected proportions matching the
source PNG's own palette, not a uniform blank fill.

This rules out, with reasonable confidence:
- The image data/encoding itself (`assets/progress/castle_stage_00_terreno_vazio.png`, byte-
  verified 288x180 RGBA, and the compiled `LV_COLOR_FORMAT_I4` array in `progress_images.c`)
  -- decodes correctly via LVGL's real indexed-image decoder.
  - The `lv_image` widget composition pattern in `castelo_app.c` (`lv_obj_set_width(s_stage_image,
  lv_pct(100))` inside a flex-column content box with padding, `LV_IMAGE_ALIGN_CENTER` default)
  -- renders correctly even under simulated heap pressure down to ~108KB free (`LV_MEM_SIZE` is
  512KB).
- The lookup chain `ratimos_progression_stage_asset_id()` -> `ratimos_progress_image_by_id()`
  -> `ratimos_progress_by_id()` -- resolves the correct descriptor for `shared_completions=0`
  and `=1` alike (both resolve to `castle_stage_00_terreno_vazio`, the first threshold).
- `src/storage/game_state.c`'s real `ratimos_storage_get_progression()`/
  `ratimos_storage_save_progression()` implementation was read directly and found to clamp
  `shared_completions` safely (`RATIMOS_PROGRESSION_MAX_COMPLETIONS = 9999`, far above the
  30-day target, but `ratimos_progression_stage_index_in()` already clamps any out-of-range
  value to the last populated stage rather than reading garbage) -- no corruption path found
  that would produce a blank render.

## What remains unexplained -- this is the actual investigation surface for this plan

The bug was reported from an INTERACTIVE session (real mouse-driven navigation through the
compiled `native_sdl` SDL2 window: home -> jogos -> conexo -> win -> back -> home -> castelo),
which this planning session's headless reproduction did not fully replicate (no SDL window, no
real multi-screen retained-heap accumulation from actually playing through conexo's full UI).
The two most likely remaining explanations, in priority order:

1. **Heap/cache pressure from a longer real session.** The headless test only ever built the
   castelo screen (plus its own minimal stub dependencies) before rendering -- free heap was
   never pushed below ~108KB, and that threshold was reached only via an artificial `lv_malloc`
   hog, not real retained screens. A real session that has already built+cached splash, home,
   jogos launcher, and conexo's own screen (which has its own grid/tile widget tree) before
   reaching castelo for the first time has genuinely less free heap at that point, and the
   288x180 stage image needs a real decode buffer (~103KB) at draw time. This is the leading
   hypothesis.
2. **An SDL-driver-specific or session-sequencing artifact** not reproducible via a headless
   manual-buffer display at all. Lower priority: LVGL's own `lv_sdl_window_create()` driver is
   a widely-used generic reference implementation with no evidence of per-image-size bugs, and
   every OTHER image (including the SAME 288x180-adjacent-sized game grids) renders fine for
   the user in the same session.
</investigation_notes>
