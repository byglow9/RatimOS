# Phase 02.1 — Validation Strategy

> Per-phase validation contract for feedback sampling during execution.

---

## Test Infrastructure

| Property | Value |
|----------|-------|
| **Framework** | PlatformIO native Unity test runner (`unity`), confirmed via existing `test/test_storage/test_storage.c` |
| **Config file** | `platformio.ini`'s `[env:native_sim]` (`test_build_src = yes`) — no separate test-specific config file |
| **Quick run command** | `pio test -e native_sim -f test_<suite>` (single suite) |
| **Full suite command** | `pio test -e native_sim` |
| **Estimated runtime** | ~60s per suite, ~5-6 min full suite (per existing suite timings from Phase 1/2) |

---

## Sampling Rate

- **After every task commit:** Run the specific new test file's quick command (e.g. `pio test -e native_sim -f test_jogos_sudoku`)
- **After every plan wave:** `pio test -e native_sim` (full suite, matches existing `test_storage`/`test_sync_unit`/`test_sync_integration` pattern)
- **Before `/gsd-verify-work`:** Full suite must be green, plus the manual UAT click-through for all 5 games (ROADMAP success criteria 2-4) and a visual side-by-side comparison against colombiaOS for success criterion 1
- **Max feedback latency:** ~60s (single suite)

## Security Domain (ASVS Level 1, block on High)

> Fully offline, single-device, single-user, no network calls, no auth surface — most ASVS categories don't apply. Two do, because of this phase's new write-persistence surface.

| ASVS Category | Applies | Standard Control |
|---------------|---------|-------------------|
| V2 Authentication | No | No login/auth surface |
| V3 Session Management | No | No sessions — local single-process app |
| V4 Access Control | No | No multi-user/permission model |
| V5 Input Validation | **Yes** | The new game-state/progression save file is read back from disk at every relaunch — treat as untrusted input (could be corrupted by an interrupted write, a full SD card in a future hardware phase, or manual tampering): validate size/bounds before trusting any field (clamp `shared_completions` to a sane max, reject an out-of-range `ratimos_game_kind_t` enum value) rather than trusting the blob blindly. Mirrors the existing `letters.c`/`photos.c` safe-default-title defensive pattern. |
| V6 Cryptography | No | Save data is not secret — no encryption needed |
| V12 File/Path Handling | **Yes** | Continue existing discipline (`letters.c`/`photos.c`): fixed, hardcoded file paths for save data, never built from user/content-derived input |

**Known threat patterns:**

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|-----------------------|
| Corrupted/truncated save file crashes the app on next launch | Denial of Service (self-inflicted) | Validate loaded blob's size/fields before use; fall back to a fresh/default state on validation failure, never crash or propagate garbage |
| Out-of-bounds array index from a malformed persisted enum/board-cell value | Tampering (low likelihood, general embedded-C defensive norm) | Bounds-check every enum/array index sourced from a loaded save blob before using it to index into a fixed-size C array |
