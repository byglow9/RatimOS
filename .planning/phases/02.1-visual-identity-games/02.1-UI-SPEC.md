# Phase 02.1 — UI Design Contract

> Visual and interaction contract for RatimOS's icon/typography pass (VISUAL-01) plus five
> game screens and the garden/castle progression display (JOGOS-01..05, PROGRESSAO-01).
> Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **Medium note:** RatimOS is an embedded LVGL 9.5.0 / C firmware UI (ESP32-S3, 320×480
> portrait panel, currently `native_sim` PC/SDL2), not a web/React stack. The generic
> shadcn/web-component parts of the base UI-SPEC template do not apply — see "Design System"
> below for how each template concept maps onto this project instead. All screen dimensions
> in this document are computed against the actual 320×480 panel and the existing
> `ratimos_app_shell_create()` chrome budget (see "Screen Budget" below), not placeholders.

---

## Design System

| Property | Value |
|----------|-------|
| Tool | none — embedded LVGL/C project, not React/Next/Vite; the shadcn initialization gate is not applicable to this stack |
| Preset | not applicable |
| Component library | LVGL 9.5.0 built-in widgets only: `lv_obj`, `lv_label`, `lv_image`, `lv_table`, `lv_buttonmatrix`, LVGL Grid layout (`LV_USE_GRID`). No external UI component library exists or is needed. |
| Icon library | None third-party. Project-authored pixel-art sprite set (D-07) — see "Icon & Title Font Asset Pipeline" below. |
| Font | Two-tier per D-08: **body** = LVGL built-in bitmap Montserrat (14/20/28, already vendored, regular weight only); **heading/display** = new custom pixel/bitmap font converted via `lv_font_conv` — see Typography below. |

**Screen budget (all layouts in this document are computed against this):**

```
Panel: 320 x 480 px (RATIMOS_SCREEN_W / RATIMOS_SCREEN_H, theme.h)
Chrome (ratimos_app_shell_create, unchanged by this phase):
  topbar     26px
  sectionbar 24px
  bottombar  22px
  ---------------
  chrome total: 72px
Content area: 320w x 408h, with its own pad_all=10 on every side
  -> usable inner content box: 300w x 388h
```
Every per-game layout below is sized against this 300×388 usable box. Treat these numbers
as the contract; the executor should not need to re-derive them from scratch.

## Spacing Scale

**This project's spacing scale is already locked (D-16, Phase 1) and differs from the
generic 8-point default** — it is reused as-is, not reopened:

| Token | Value | Usage (existing, D-16) |
|-------|-------|-------------------------|
| xs | 4px | Tightest internal gaps (home tile icon-to-label row gap) |
| sm | 6px | Topbar internal column gaps, sectionbar title left-offset |
| comp | 8px | Panel internal padding (`ratimos_panel_create`), content row gap |
| md | 10px | Screen content padding, row/column gaps in row lists and home grid |
| lg | 16px | **New for this phase**: game-board cell gaps, digit-keypad row gaps |
| xl | 24px | **New for this phase**: section breaks inside game screens (e.g. between crossword grid and its clue strip, above/below the shared Termo keyboard) |

`lg`/`md` were locked in D-16 but not yet used anywhere in the codebase before this phase —
this phase is their first real application, for exactly the larger-grouping game-screen
purposes D-16 reserved them for.

**Exceptions (declared, not silent):**

1. **Sub-scale grid/keyboard cell sizes.** Sudoku cells, Termo/Dueto/Quarteto tiles, crossword
   cells, and Conexo tiles are sized by `(usable_width − (n−1)×gap) / n`, not by picking a
   token directly — their *gaps* still use the `xs`(4px) or `lg`(16px) tokens (see "Game
   Screen Layouts"), but the resulting cell/tile dimension itself is a derived value, documented
   per-game below.
2. **Touch targets below the 44px ideal.** Sudoku's digit keypad (~30px/key) and the shared
   Termo/Dueto/Quarteto keyboard (~28-30px/key) fall under the generic 44px touch-target
   floor because up to 10 columns must fit in a 300px-wide panel. This is an accepted,
   explicitly-flagged risk: final finger/stylus confirmation is out of this phase's scope and
   rides on Phase 3's existing passive-stylus verification (ROADMAP note), not something this
   phase can resolve on `native_sim` (mouse input doesn't surface small-touch-target problems).
   Board/tile display-only cells (never tapped directly — see per-game notes) are exempt from
   this floor entirely since they carry no touch interaction.

## Typography

**Medium constraint (documented, not a spec gap):** LVGL bitmap fonts ship exactly one weight
per compiled font — there is no bold/italic variant of Montserrat bundled with this project,
and a hand-authored pixel font is a single weight by construction. "Two weights" is therefore
satisfied by **two font families used as the weight axis**, not by a bold/regular pair within
one family:

| Role | Size | "Weight" | Line spacing (added px, on top of font metrics) |
|------|------|----------|--------------------------------------------------|
| Body | 14px (`lv_font_montserrat_14`) | regular — Montserrat, the only shipped weight | +2px |
| Label | 14px (`lv_font_montserrat_14`), differentiated by color (`RATIMOS_COLOR_TEXT_MUTED` vs `RATIMOS_COLOR_TEXT`), not size | regular — Montserrat | +1px |
| Heading | 16px, new pixel/bitmap font | **pixel-display** — the categorically bolder/blockier second "weight" tier (D-08) | +2px |
| Display | 20px, same pixel/bitmap font family as Heading | pixel-display | +3px, wrap to 2 lines centered if it would overflow 300px width |

**Where each role is used:**
- **Body** (14px Montserrat): row subtitles, game instructions/rules text, crossword clue text, letters, settings labels — unchanged from existing usage.
- **Label** (14px Montserrat, muted or accent color): sudoku cell candidate numbers, keyboard key glyphs, Conexo tile words, badges/hints — same font as Body, distinguished by color only (see Color section), never by size.
- **Heading** (16px pixel font): every `ratimos_sectionbar_create()` title going forward (`"sudoku"`, `"paciência"`, `"termo"`, `"cruzadinha"`, `"conexo"`, `"castelo"`, and the existing `"jogos"`/`"home.mem"` etc.) — this is the literal "screen/section titles" scope of D-08.
- **Display** (20px pixel font): win/lose/celebration banner text inside game screens (e.g. "resolvido!", "você venceu!"), and the progression screen's milestone headline (e.g. "castelo completo!").

**Technical constraint for the executor:** the sectionbar's `LV_SYMBOL_OK` checkmark icon and
any other `LV_SYMBOL_*` glyphs **stay on the default Montserrat symbol font** — custom pixel
fonts converted via `lv_font_conv` do not include LVGL's private-use-area icon glyphs. Only
the adjacent title *label* switches to the pixel font; icon glyphs never do.

**Title/display font candidate (D-08, needs a verification task before lock):**
- **Primary candidate:** *Press Start 2P* (Google Fonts, SIL OFL 1.1 — permissive, matches the
  logo's blocky 16-bit-chess-piece aesthetic closely). Confirmed OFL-licensed and confirmed to
  include accented Latin/Portuguese glyph support per font-distributor documentation
  `[MEDIUM confidence — not independently glyph-by-glyph verified this session]`.
- **Fallback candidate:** *Pixel Operator* (also OFL) if Press Start 2P's actual rasterized
  output is missing any of the required PT-BR glyphs below.
- **Required verification task (block before locking the font in a plan):** run `lv_font_conv`
  against the candidate TTF with the exact glyph range this project needs, and visually confirm
  every glyph renders (no boxes/missing-glyph fallback):
  ```
  lv_font_conv --font PressStart2P-Regular.ttf --size 16 --bpp 4 --format lvgl \
    --range 0x20-0x7E \
    --symbols "áàãâéêíóôõúçÁÀÃÂÉÊÍÓÔÕÚÇ" \
    -o ratimos_font_title_16.c
  # repeat with --size 20 for the Display-tier font asset
  ```
  (Flag structure per Round 1's Environment Availability: if Node/npm is unavailable, fall back
  to the browser-based LVGL Font Converter at lvgl.io/tools/fontconverter with the same range.)

## Color

**Base palette is locked (D-17, Phase 1) — do not modify these 6 values, do not introduce new
brand/chrome colors:**

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `RATIMOS_COLOR_BG` `#000000` | Screen backgrounds, empty space on every game board |
| Secondary (30%) | `RATIMOS_COLOR_PANEL` `#2a123f` | Panels, cards, topbar/sectionbar/bottombar, unfilled game-board cell backgrounds, keyboard key backgrounds |
| Accent (10%) | `RATIMOS_COLOR_ACCENT` `#e6010f` | **Reserved for, exhaustively:** back-button icon+label, sectionbar checkmark, launcher row icon-badge fill, sudoku selected-cell border, Termo/Dueto/Quarteto current-guess-row outline, Conexo "submit"/primary-action button, progression milestone ring/highlight, the currently-selected sudoku difficulty pill. Never used as a gameplay-feedback color (see Game Semantic Colors below) and never as a second "everything interactive" catch-all. |
| Tertiary (state) | `RATIMOS_COLOR_PANEL_ACTIVE` `#4e2277` | Pressed/selected/active background state — selected sudoku cell fill, pressed keyboard key, selected (not-yet-submitted) Conexo tile, non-selected sudoku difficulty pills' hover state |
| Text | `RATIMOS_COLOR_TEXT` `#f5f2f8` | Primary text on dark backgrounds |
| Text muted | `RATIMOS_COLOR_TEXT_MUTED` `#a997ba` | Secondary/Label-tier text, bottombar hints, muted subtitles |

**New this phase — Game Semantic Feedback Colors (net-new, not a D-17 reopening):** D-17 locked
*brand/chrome* colors; it made no provision for gameplay correctness feedback because no games
existed yet. Termo/Dueto/Quarteto and Conexo need semantic states the 6 brand colors cannot
honestly express (a red "accent" cannot also mean "letter correct"). These are proposed as new
`RATIMOS_COLOR_*` additions to `theme.h`, stylistically consistent (desaturated, retro-pixel,
readable on `#000000`/`#2a123f`), and used **only inside game-board feedback**, never for
chrome/CTAs:

| Semantic role | Value | Usage |
|---------------|-------|-------|
| Correct (letter right position) | `RATIMOS_COLOR_GAME_CORRECT` `#2f8f4e` | Termo family: solved-position letter tile |
| Present (letter in word, wrong position) | `RATIMOS_COLOR_GAME_PRESENT` `#d99a1b` | Termo family: present-but-misplaced letter tile |
| Absent (letter not in word) | `RATIMOS_COLOR_GAME_ABSENT` `#3a3a42` | Termo family: absent letter tile — a **neutral desaturated gray**, deliberately not reusing `PANEL`'s violet hue, so it reads as "ruled out" rather than "just unfilled" |
| Conexo — easiest group | `RATIMOS_COLOR_CONEXO_YELLOW` `#d9a520` | Solved-category band background (difficulty tier 1) |
| Conexo — group 2 | `RATIMOS_COLOR_CONEXO_GREEN` `#3f8f4e` | Solved-category band background (difficulty tier 2) |
| Conexo — group 3 | `RATIMOS_COLOR_CONEXO_BLUE` `#2f6fa8` | Solved-category band background (difficulty tier 3) |
| Conexo — hardest group | `RATIMOS_COLOR_CONEXO_PURPLE` `#8a3fbe` | Solved-category band background (difficulty tier 4) — deliberately more saturated than `PANEL_ACTIVE`'s `#4e2277` so the two are visually distinct |

**Accessibility note (discretionary follow-up, not blocking):** correct/absent feedback should
not rely on color alone where practical — consider pairing each Termo tile's color with a
distinct border weight or a small corner glyph so red-green colorblind players aren't solely
dependent on the green/gray distinction. Not required for this phase's completion, flagged for
planner discretion.

**Destructive:** No new destructive color is introduced. The one destructive action this phase
has (resetting an in-progress game, see Copywriting) uses `RATIMOS_COLOR_ACCENT` for the
confirming button, consistent with accent already meaning "the button that matters right now"
throughout the existing UI — a second red would be redundant on a screen that already uses red
as its sole warm color.

## Icon & Title Font Asset Pipeline (D-07)

**Concrete pipeline recommendation** (resolves D-07's "research and propose" discretion):

1. Author a single pixel-art sprite sheet PNG (external tool — **Piskel**, free/browser-based,
   or **Aseprite** if the developer wants to buy a proper pixel-art editor) containing 6 icons
   at **32×32px** each: `jogos` (generic app icon — reuse a simplified castle-tower motif from
   the logo) + one icon per game (`sudoku`, `paciencia`, `termo`, `cruzadinha`, `conexo`).
   Match the logo's red/orange/purple gradient + dark outline treatment; icons live on a
   transparent or `#000000` background.
2. Add `tools/convert_icons.py`, a sibling to the existing `tools/convert_logo.py` (same
   Pillow-based approach, already a project dependency — no new Python package), that slices
   the sheet into per-icon `lv_image_dsc_t` C arrays and emits `src/ratimos/icons.c`/`.h`
   (one `extern const lv_image_dsc_t` per icon, e.g. `ratimos_icon_sudoku_desc`).
3. Use `LV_COLOR_FORMAT_I4` (16-color indexed palette) instead of the logo's RGB565 — pixel art
   icons use few colors, and I4 is ~4x smaller in flash than RGB565, which matters once these
   compile into the real ESP32-S3 firmware image later.
4. Replace `ratimos_badge_create()`'s circle+letter rendering with an `lv_image` at the same
   **28×28px slot size** (unchanged — minimizes disruption to `row_list.c`/home-screen tile
   layout) rendering the matching icon, masked to a circle if the sprite itself isn't already
   circular. If 28px proves too small for legible pixel detail once real art is produced, grow
   the slot to 32px (a 4px increase, itself a locked `xs` token step) — flag this as a
   plan-time visual check, not a locked number.
5. Progression stage art (garden/castle images, see below) and the 5 per-game exclusive
   decorative unlock sprites reuse the same `convert_icons.py`-style pipeline, not a new script.

**Title font conversion:** see Typography section above for the exact `lv_font_conv` invocation
and required PT-BR glyph verification step.

## Game Screen Layouts

Every game screen is built via `ratimos_app_shell_create(section_label, bottom_right_hint)`
(unchanged chrome) with its own content mounted into `shell.content` (300×388px usable box).
Bottom-right hint text and back-button label follow the existing `"voltar"` convention.

### Sudoku (JOGOS-01)

| Element | Spec |
|---------|------|
| Difficulty/mode selector | Row of 4 pill toggle buttons (`fácil` / `médio` / `difícil` / `diário`), height 28px, `lg`(16px) gap below. Selected pill: `PANEL_ACTIVE` background + `ACCENT` border/text. Unselected: `PANEL` background + `TEXT_MUTED` text. |
| Board | 9×9 grid, **32×32px cells** (288×288px board, centered), 1px hairline between cells, 2px `ACCENT`-tinted divider every 3rd row/column (3×3 box separation) |
| Selected cell | `PANEL_ACTIVE` fill + `ACCENT` 2px border |
| Digit keypad | Row of 10 keys (`1`-`9` + `apagar`/erase), ~30px wide × 36px tall each, `PANEL` background, `xs`(4px) gaps |
| Bottom-right hint | `"números 1-9"` |
| Win banner | Display-tier text `"resolvido!"`; if daily mode, append `"+1 no castelo"` beneath it |

### Paciência / Klondike (JOGOS-01)

| Element | Spec |
|---------|------|
| Top zone | Stock + waste pile (left cluster) + 4 foundation piles (right cluster); card size 40×56px; `xs`(4px) gap within a cluster, `lg`(16px) gap between the two clusters |
| Tableau | 7 columns, card 38×54px, vertical cascade overlap 16px between stacked cards in a column, `xs`(4px) horizontal gap between columns |
| Move legality | Enforced per move-type validation function (tableau→tableau, tableau→foundation, stock→waste) per RESEARCH's Don't-Hand-Roll guidance — illegal drops must visibly snap back, never silently accept |
| Bottom-right hint | `"arraste as cartas"` |
| Win banner | Display-tier text `"venceu!"` |

### Termo / Dueto / Quarteto (JOGOS-03)

**Resolves RESEARCH's flagged open layout question with concrete numbers:**

| Mode | Boards | Board layout | Tile size | Visible rows |
|------|--------|---------------|-----------|---------------|
| Termo | 1 | Single board, full width, centered | ~40px square | all 6 rows visible, no scroll |
| Dueto | 2 | Side-by-side, each ~145px wide | ~26px square | all 7 rows visible, no scroll |
| Quarteto | 4 | 2×2 grid, each ~145×125px | ~22px square | **only 5 most-recent rows visible per board; each board scrolls independently (`lv_obj` scrollable) to reveal earlier guesses.** 9 rows at full size cannot fit the vertical budget legibly — a fixed 5-row viewport + scroll is the concrete resolution, not an unresolved gap. |

**Sizing priority rule (governs all 3 modes uniformly):** the shared keyboard is fixed first
(min 32px key row height, touch priority) → mode/tries status label fixed at ~20px → boards
receive whatever vertical space remains, divided evenly among visible rows, clamped between
22px (min legible) and 48px (max, avoids oversized Termo tiles).

**Keyboard:** ONE shared, non-split, neutral-colored `lv_buttonmatrix` (PT-BR layout, 3 rows,
`PANEL` key background, `TEXT` glyphs) below all boards. **Explicitly not split/per-board
colored** (deviating from Dordle/Quordle's split-key convention) — resolves RESEARCH's flagged
open decision in favor of legibility on a 320px-wide screen; color feedback lives only on each
board's own guess-row tiles (Correct/Present/Absent colors from the Color section above).

**Guess submission model:** one shared text buffer; submitting applies the same guess to every
still-unsolved board simultaneously (Dordle/Quordle precedent, RESEARCH round 2). A solved
board visually freezes (dims its keyboard-irrelevant rows, e.g. slight opacity reduction) while
others keep playing.

| Bottom-right hint | `"digite uma palavra"` |
| Win banner (per board solved) | Display-tier `"acertou!"` |
| Loss (tries exhausted, board(s) unsolved) | `"não foi dessa vez"` + reveal the unsolved answer(s) in `TEXT_MUTED` |

### Cruzadinha (JOGOS-04)

**Refines RESEARCH's rough 13×13/15×15 placeholder with an actual screen-budget calculation:**
a 13×13 grid in a 300px-wide panel yields ~23px cells — workable but cramped for tap-to-enter
letter interaction. **This phase's puzzles target a 9×9 grid maximum** (up to 11×11 acceptable
if a specific puzzle's word list genuinely needs it), yielding **~30-32px cells**, matching
Sudoku's cell size and keeping letter-entry taps comfortable.

| Element | Spec |
|---------|------|
| Grid | Up to 9×9 (11×11 max), ~30px cells, numbered start-cells per the standard numbering algorithm (RESEARCH: scan left-to-right/top-to-bottom, number a cell if it starts an across and/or down entry) |
| Clue interaction | **Contextual, not a permanently-visible full list** (resolves the vertical-space squeeze): tapping a word (across or down) shows *that word's single clue* in a fixed ~40px clue strip above the grid, with a small `▲`/`▼` "próxima palavra" affordance to cycle through remaining unsolved clues. |
| Secondary affordance | An optional `"ver todas as dicas"` toggle opens a full-screen scrollable numbered clue list (satisfies JOGOS-04's literal "numbered clue" requirement for players who want to browse), separate from the default compact play view |
| Letter entry | Tapping a cell selects it; the existing project's shared keyboard pattern (or a simple on-screen A-Z `lv_buttonmatrix`) enters the letter |
| Bottom-right hint | `"toque numa palavra"` |
| Win banner | Display-tier `"cruzadinha completa!"` |

### Conexo (JOGOS-05)

| Element | Spec |
|---------|------|
| Grid | 4×4 word tiles, ~72×56px each, `xs`(4px) gaps. Tile text uses Label-tier (14px Montserrat), `LV_LABEL_LONG_MODE_WRAP` for long words |
| Selection | Tap to select (max 4 at once); selected tile = `PANEL_ACTIVE` fill + `ACCENT` border |
| Mistake counter | `"erros: X/4"` label above the action row, `TEXT_MUTED` |
| Actions | Two pill buttons, ~146px wide × 32px tall each: `"embaralhar"` (shuffle, neutral `PANEL`) and `"enviar"` (submit, `ACCENT` — the one primary-action use of accent per the Color contract) |
| Solved group | Animates/moves to a solved-category band at the top, colored by its difficulty tier (Color section's 4 Conexo colors), showing the category name in Label-tier text |
| Loss handling | After 4 mistakes, remaining groups auto-reveal with `"quase lá — aqui estão as categorias"` rather than a hard "you lost" state |
| Bottom-right hint | `"toque 4 para agrupar"` |
| Win banner | Display-tier `"categorias completas!"` |

## Progression System UI (PROGRESSAO-01)

**Resolves CONTEXT.md's explicitly-open "needs its own home" question:**

- **Home screen:** add one new full-width tile below the existing 2×2 app grid (there is
  ~130-140px of unused vertical slack already present in `home_screen.c`'s content column — see
  Screen Budget math; no existing tile needs to shrink). New tile: ~300×100px, showing a small
  thumbnail of the current milestone-stage image + a one-line status (`"dia X"` or the current
  stage's short label), tappable to open the dedicated screen below. Icon/tile follows the same
  `ratimos_panel_create()` styling as every other home tile.
- **Dedicated screen:** new `"castelo"` section (`ratimos_app_shell_create("castelo", ...)`),
  showing the current milestone-stage image full-width, a numeric `"dia X de N"` (or
  `"completo!"` at the end state) caption in Heading-tier pixel font, and a row of up to 5 small
  per-game exclusive-unlock icons beneath it (locked/grayscale via reduced opacity for
  not-yet-unlocked games, full color for unlocked ones), labeled `"conquistas"`.
- **Status copy by stage:** `0` completions → `"o castelo está apenas começando"`; mid-range →
  `"dia {shared_completions} de {N}"`; final stage reached → `"castelo completo! parabéns"`.
- **Asset naming:** each of the ~6 stage images is produced via the same PNG→`lv_image_dsc_t`
  pipeline as the logo/icons, stored in `src/ratimos/progress_images.c` with variable names
  matching the progression manifest's `asset_id` strings 1:1 (e.g. `castle_stage_00_empty_grounds`
  → `ratimos_progress_castle_stage_00_empty_grounds_desc`), so the runtime string→image lookup
  table the RESEARCH doc proposes has an unambiguous naming convention to follow.
