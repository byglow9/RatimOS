# Phase 02.1: Code Review Report

**Reviewed:** 2026-09-10T00:00:00Z
**Depth:** standard
**Files Reviewed:** 61
**Status:** issues_found

## Summary

Reviewed the visual-identity + 5-games phase: icon/progression art pipeline,
title font conversion, the 5 game engines (sudoku, klondike/paciência, termo,
cruzadinha, conexo) and their LVGL screens, the shared puzzle-history/daily-seed
helpers, the `game_state`/`progression` storage domain, and the asset-generation
tooling. The engines themselves are careful and well-tested (unique-solution
sudoku generator, duplicate-letter-safe Wordle scoring, structural crossword
integrity tests, Fisher-Yates shuffles seeded off a local xorshift PRNG rather
than libc `rand()`).

The one BLOCKER is a cross-cutting progression-integrity gap: four of the five
games (sudoku's modo diário, termo's 3 modes, conexo, cruzadinha) can have their
"one castle credit per day" guarantee bypassed by using the games' own "novo
jogo" / mode-switch affordance, because `ratimos_storage_record_daily_win()` has
no day-level dedup at the storage layer and the client-side `daily_win_recorded`
flag is reset by the very same action that is supposed to only reset the board.
`paciência` (`paciencia.c`) gets this right by explicitly tagging a manual redeal
as non-daily (`ratimos_klondike_deal(&s_state, fresh_seed(), false)`) so a
manual replay can never re-credit; the other four games regenerate a fresh
*daily*-flagged/daily-seeded session on reset, which can be re-solved and
re-credited the same day. Given the whole point of `PROGRESSAO-01` is a slow,
~30-day reveal of the castle/garden as a scarce, meaningful gift mechanic, this
gap lets a player trivially finish the "castelo completo" milestone in one
sitting, undermining a stated core-value feature.

The remaining findings are smaller robustness/consistency gaps: a missing
ASCII validation on crossword clue text (unlike answers), a data-integrity risk
around the daily 24h→32-slot-per-day seed scheme documented but not tested for
in `daily_seed.c`, and a few minor code-quality items.

## Critical Issues

### CR-01: "novo jogo" / mode-switch lets sudoku, termo, conexo, and cruzadinha re-credit the same daily win multiple times

**File:** `src/ratimos/apps/jogos/sudoku.c:372-386` (`confirm_restart_cb` / `SUDOKU_PENDING_RESET` path calling `switch_to_mode(s_state.mode)`), `src/ratimos/apps/jogos/termo.c:164-170` (`switch_to_mode`), `src/ratimos/apps/jogos/conexo.c:389-397,405-414` (`start_new_board` / `confirm_restart_cb`), `src/ratimos/apps/jogos/cruzadinha.c:196-215,507-516` (`start_new_puzzle` / `confirm_restart_cb`), and the storage-layer root cause at `src/storage/game_state.c:373-392` (`ratimos_storage_record_daily_win`)

**Issue:**
`ratimos_storage_record_daily_win()` has no day-scoped idempotency at all — it
unconditionally increments `shared_completions` and sets the exclusive-unlock
flag every time it is called (this is explicitly proven by
`test_record_daily_win_twice_increments_counter_but_flag_stays_one` in
`test/test_storage_game_state/test_storage_game_state.c`). The *only* guard
against double-crediting the shared castle/garden counter is each game's own
in-memory/persisted `daily_win_recorded` byte, checked before calling
`ratimos_storage_record_daily_win()`.

That guard is defeated by the "novo jogo" / troca-de-modo flow in 4 of the 5
games, because those flows regenerate the ENTIRE state via `memset` and refill
it from the deterministic *daily* seed again, which resets `daily_win_recorded`
back to 0 while still producing the *daily* puzzle (same content, since the
seed is a pure function of `ratimos_daily_index()`):

- **sudoku** (`sudoku.c`): `mode_pill_clicked_cb` → confirm → `confirm_restart_cb`
  → `switch_to_mode(s_state.mode)` when `s_pending_action == SUDOKU_PENDING_RESET`,
  or `switch_to_mode(s_pending_mode)` on a mode switch. `switch_to_mode()` calls
  `generate_for_mode()`, which for `RATIMOS_SUDOKU_DIARIO` reseeds with
  `ratimos_daily_seed(RATIMOS_GAME_SUDOKU)` — the same value all day — and
  `memset`s the fresh state, zeroing `daily_win_recorded`. A player who already
  won today's diário puzzle can hit "novo jogo", re-solve the (identical) board,
  and `ratimos_storage_record_daily_win(RATIMOS_GAME_SUDOKU)` fires again.
- **termo** (`termo.c`): `switch_to_mode()` (line 164) calls
  `ratimos_termo_start_daily(&s_state, mode, ratimos_daily_index())` unconditionally
  on every mode-pill click, which `memset`s the whole state including
  `daily_win_recorded`. Switching away from an already-won mode and back to it
  regenerates the same day's boards and clears the win-recorded guard, allowing
  a second credit.
- **conexo** (`conexo.c`): "novo jogo" → `confirm_restart_cb` → `start_new_board()`
  (line 389), which always seeds via `ratimos_daily_seed(RATIMOS_GAME_CONEXO)`
  and `memset`s `state` (clearing `daily_win_recorded`), with no "already played
  today" concept at all — unlike sudoku/termo there isn't even a non-daily mode
  to fall back to, so *every* replay of conexo is eligible to credit the castle.
- **cruzadinha** (`cruzadinha.c`): identical pattern via `start_new_puzzle()`
  (line 196) called from `confirm_restart_cb` (line 507).

Contrast with **paciência** (`paciencia.c:527-541`, `confirm_restart_cb`), which
gets this right: a manual "novo jogo" always deals with
`ratimos_klondike_deal(&s_state, fresh_seed(), false)` — the `daily` flag is
explicitly `false`, and `handle_win_credit_if_needed()` (line 208) only credits
when `s_state.daily` is true, so a manual redeal can *never* re-credit no matter
how many times it's replayed. This is exactly the invariant the other four games
need and don't have.

**Impact:** Any player can trivially inflate `shared_completions` (the shared
castle/garden progression counter, capped only at 9999) far beyond the intended
~1-per-day-per-game pace, completing the "castelo completo" ~30-day milestone
in a single sitting by repeatedly hitting "novo jogo"/switching modes and
re-solving the same deterministic daily puzzle. This directly undermines
`PROGRESSAO-01`'s stated design intent (a slow, meaningful reveal timed to
real daily use) and the project's core-value framing of the device staying
"alive" over time.

**Fix:** Make the "already credited today" guard survive a client-side reset,
either by:
1. Adding day-scoping at the storage layer — e.g. persist the `ratimos_daily_index()`
   value alongside `shared_completions`/`game_exclusive_unlocked` in
   `ratimos_progression_state_t`/`progression_record_t`, and have
   `ratimos_storage_record_daily_win()` itself check "have I already recorded a
   win for this game on this day-index?" before incrementing (this is the most
   robust fix — it protects every current and future caller, not just the ones
   that remember to check a client flag), or
2. At minimum, stop clearing `daily_win_recorded` on a "novo jogo"/mode-switch
   reset for daily-seeded content: preserve that single byte (like conexo/
   cruzadinha already preserve `history` across a reset) instead of `memset`-ing
   the whole state, and gate any regenerate-with-daily-seed path so it can't run
   again if the day's win is already recorded (mirroring how paciência tags a
   manual redeal `daily=false`).

## Warnings

### WR-01: Crossword clue text has no ASCII/charset validation, unlike answers

**File:** `tools/generate_crossword.py:88-94` (`validate_clue`)
**Issue:** `validate_answer()` explicitly rejects non-ASCII/non-uppercase input
(`answer.isascii()`), but `validate_clue()` only checks length (1-90 chars),
with no `isascii()` check. The embedded LVGL bitmap fonts used throughout this
project are ASCII-only (explicitly called out in
`src/ratimos/apps/jogos/conexo_puzzles.c:15-17` and the crossword README's own
"sem acento" convention for answers). If a future clue is authored with
accented PT-BR characters, two things can go wrong: (1) the accented glyphs
render as empty boxes/garbage on-device, and (2) because the check counts
Python string length in *characters*, not UTF-8 *bytes*, a 90-character clue
using multi-byte accented characters can exceed the fixed
`char clue_text[96]` C buffer's byte capacity, risking silent truncation
without a NUL terminator when the string literal is emitted into the generated
`.c` array.
**Fix:** Add an ASCII check to `validate_clue()` mirroring `validate_answer()`,
e.g. `if not clue.isascii(): raise CrosswordError(...)`, and additionally
assert the UTF-8 byte length (not just character count) fits within 95 bytes
(`len(clue.encode("utf-8")) <= 95`).

### WR-02: `daily_seed.c` silently returns a colliding seed if `stream` values are ever allowed to reach 32

**File:** `src/ratimos/apps/jogos/daily_seed.c:16-21`, `termo_engine.c:97-100`
**Issue:** `ratimos_daily_seed()` reserves a 32-wide slot per day
(`ratimos_daily_index() * 32u + stream`) and the comment says "32 = folga
suficiente para os 5 jogos de hoje mais os modos extras do termo... sem que
dois fluxos colidam". `termo_daily_seed()` uses offset `8 + mode` (mode ∈ 0..2,
so offsets 8-10), and the five games use raw `ratimos_game_kind_t` values 0-4.
Both live comfortably inside the 32-wide window today, but there is no
compile-time or runtime assertion tying `RATIMOS_GAME_COUNT` and
`RATIMOS_TERMO_MODE_COUNT`'s highest offset to the `32u` constant — a 6th game
or 4th termo mode added later (offset 5 or 11, both still < 32, so this
specific overflow wouldn't trigger yet, but the pattern of "manually verify it
still fits" is exactly the kind of invariant that silently breaks when nobody
re-reads this comment) has no enforced protection against eventually exceeding
32 distinct streams sharing one day's 32-wide window, which would silently
alias two unrelated daily streams to the same seed with no build or runtime
failure.
**Fix:** Add a `_Static_assert` (or equivalent runtime assertion reachable from
a test) tying `RATIMOS_GAME_COUNT` and the termo mode offset ceiling to the
`32u` stride, e.g. `_Static_assert(RATIMOS_GAME_COUNT + <max termo offset> < 32, ...)`
so a future 6th game/4th termo mode fails the build instead of silently
colliding seeds.

### WR-03: `sudoku.c` "novo jogo" reset on a non-diário mode still routes through `switch_to_mode(s_state.mode)`, discarding an already-solved-but-unsaved distinction between "reset while solved" and "reset mid-game"

**File:** `src/ratimos/apps/jogos/sudoku.c:372-386`
**Issue:** `confirm_restart_cb`'s `SUDOKU_PENDING_RESET` branch always calls
`ratimos_storage_clear_game_state()` then `switch_to_mode(s_state.mode)`
regardless of whether the current board was solved, mid-progress, or freshly
generated. This is minor by itself, but combined with CR-01, it means
"novo jogo" on an *already-solved* diário board is the primary user-visible
trigger for the double-credit bug — the pill is available "o tempo todo, nao
so apos vencer" per the comment on line 406-409, so a curious/re-engaged player
finishing the daily puzzle and then tapping "novo jogo" out of habit (common
pattern from other daily-puzzle apps that reset for the *next* day) will
silently re-credit the castle counter.
**Fix:** Once CR-01 is fixed at the storage layer, this resolves itself; if
only fixing client state, explicitly special-case "reset while `s_state.mode
== RATIMOS_SUDOKU_DIARIO && s_state.solved`" to warn or to not regenerate a
diário board at all (redirect to a non-crediting practice board) rather than
silently allowing a second diário attempt same-day.

### WR-04: `render_clue_list` / clue-list overlay rows keyed by raw array index without validating `RATIMOS_CRUZADINHA_MAX_WORDS` split invariant

**File:** `src/ratimos/apps/jogos/cruzadinha.c:334-361`
**Issue:** `render_clue_list()` fills `s_clue_list_across_row`/`s_clue_list_down_row`
(each sized `RATIMOS_CRUZADINHA_MAX_WORDS`) by incrementing `across_count`/
`down_count` per word without ever checking that either counter itself stays
`< RATIMOS_CRUZADINHA_MAX_WORDS`. Today this is safe only because
`pz.word_count <= RATIMOS_CRUZADINHA_MAX_WORDS` is enforced elsewhere (by the
generator and by `_Static_assert`-backed struct sizing), so `across_count +
down_count <= word_count <= MAX_WORDS`, which bounds each individually. But
there is no defensive bounds check at the point of use (`s_clue_list_across_label[across_count]`),
so if that invariant is ever violated by a future bank change or a corrupted
restored `s_puzzle` (note: `s_puzzle` is not itself round-tripped through the
save file, but it is populated from `ratimos_cruzadinha_get_puzzle()` using a
`puzzle_index` that IS validated on restore, so this is currently safe — but
fragile) it becomes an out-of-bounds array write with no guard rail, unlike
most other loops in this file which do bound against `RATIMOS_CRUZADINHA_MAX_WORDS`
or `RATIMOS_CRUZADINHA_MAX_DIM` explicitly.
**Fix:** Add an explicit `if (across_count >= RATIMOS_CRUZADINHA_MAX_WORDS) break;`
(and same for `down_count`) inside the loop for defense-in-depth, matching the
bounds-checking discipline used everywhere else in this codebase (e.g.
`cruzadinha_engine.c`'s repeated `&& i < RATIMOS_CRUZADINHA_MAX_WORDS` guards).

### WR-05: `lv_conf.h`'s documented per-screen heap leak is a real, acknowledged defect left unfixed for native_sim

**File:** `lv_conf.h:15-31`
**Issue:** The comment openly documents that every `src/ratimos/apps/*.c`
screen is cache-once (built once, never deleted), which is fine by itself, but
also states the *general* pattern of "build a brand-new lv_obj_t screen on
every visit with no delete-on-navigate-away" causes heap exhaustion after only
3-4 visits at the LVGL default 64KB heap, "fixed" here only by bumping
`LV_MEM_SIZE` to 512KB for `native_sim`. This is an accepted, explicitly-flagged
tech-debt item (not a new defect introduced by this phase) but is worth
surfacing in this review because this phase adds 5 more heavyweight cache-once
screens (sudoku/paciência/termo/cruzadinha/conexo, each building 81/364/multiple
hundred/121+/16+ child objects respectively) on top of the ones the comment
already accounts for, further increasing peak static heap usage on `native_sim`
and leaving the underlying "hardware-measured LV_MEM_SIZE + real
cache-or-delete-on-navigate fix" fully deferred to Phase 3, as noted.
**Fix:** No action required for this phase (already tracked), but flagging so
the Phase 3 hardware-migration checklist doesn't lose this given the scope of
new cache-once screens just added.

## Info

### IN-01: `ratimos_conexo_shuffle` reseeds with `mistakes + 1` producing very low-entropy/small seed values for early mistakes

**File:** `src/ratimos/apps/jogos/conexo.c:375-384` (`shuffle_clicked_cb`)
**Issue:** The manual "embaralhar" (shuffle) button reseeds via
`ratimos_daily_seed(RATIMOS_GAME_CONEXO) + s_state.mistakes + 1u`. Since
`ratimos_daily_seed()` already returns a large, day-derived value, adding a
small integer (`mistakes` is 0-4) just nudges the seed slightly; this is a
correctness non-issue (xorshift-style PRNGs used elsewhere in this codebase
don't need high-entropy seeds), but worth noting that two different manual
shuffles performed with the same mistake-count on the same day (e.g. shuffle
right after opening the game, without having made any mistakes yet, on two
different app visits within the day) will always produce the *exact same*
shuffle result, which may read as "broken" if a user expects "shuffle" to mean
"something visibly different happens" — currently masked by the fact that
`s_state.tile_word` retains order between visits (persisted), so the resulting
permutation still differs based on the tiles' state at shuffle time, but the
underlying seed-selection logic is worth a one-line comment clarifying this is
intentional.
**Fix:** No functional fix required; consider documenting the intentional
low-variance seed choice, or incorporate a monotonically increasing
per-session shuffle counter instead of `mistakes` if "shuffle always looks
different" becomes a UX requirement later.

### IN-02: `card_label_text`'s suit-letter table uses Portuguese initials without a comment cross-reference to color mapping

**File:** `src/ratimos/apps/jogos/paciencia.c:109-122`
**Issue:** Minor readability nit: `SUIT_CHARS = { 'P', 'O', 'C', 'E' }` (paus/
ouros/copas/espadas) is commented, which is good, but the file doesn't
cross-reference that `ratimos_card_is_red()` in `klondike_engine.h` classifies
copas(2)/ouros(1) as red — a reader modifying one table without the other
(e.g. reordering `RATIMOS_SUIT_*` defines) would not get a compiler error, only
a visually-wrong card color/letter pairing at runtime. Not a bug today (values
are consistent), just a maintainability trap given the two tables live in
different files.
**Fix:** Add a one-line comment in `paciencia.c` cross-referencing
`ratimos_card_is_red()`/`RATIMOS_SUIT_*` order dependency, or better, derive
`SUIT_CHARS` indices directly from the `RATIMOS_SUIT_*` macros instead of a
positional literal array.

### IN-03: `sudoku.c` keypad handler recomputes `digit` via `text[0] - '0'` without validating `text` is a single ASCII digit before subtraction

**File:** `src/ratimos/apps/jogos/sudoku.c:320-338` (`keypad_value_changed_cb`)
**Issue:** `uint8_t digit = (strcmp(text, "apagar") == 0) ? 0 : (uint8_t) (text[0] - '0');`
relies entirely on `SUDOKU_KEYPAD_MAP` (a fixed, hard-coded button matrix map)
only ever containing `"1".."9"` or `"apagar"` — which is true today — but there
is no defensive validation that `text[0]` is actually an ASCII digit before the
subtraction, unlike `ratimos_sudoku_set_cell()` downstream which does bounds-
check `digit > 9`. If `text` were ever something else (e.g. a future keypad
relabeling), this would silently compute a nonsensical `digit` value rather
than being caught at the point of parsing. `ratimos_sudoku_set_cell()`'s own
`digit > 9` check happens to save this from being exploitable today, but the
lack of a local guard is inconsistent with the "never trust input, validate at
the boundary" discipline evident everywhere else in this codebase (e.g.
`cruzadinha_engine.c`'s `isalpha()` check in `ratimos_cruzadinha_set_letter()`).
**Fix:** Add `if (!isdigit((unsigned char) text[0])) return;` before computing
`digit`, matching the defensive style used in `cruzadinha.c`/`termo.c`'s
keyboard handlers.
