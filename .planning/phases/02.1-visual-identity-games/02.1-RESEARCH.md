## Summary

This phase has two genuinely distinct halves that should be planned (and likely wave-sequenced) separately: (1) a **visual identity pass** — pixel-art icons + a retro bitmap title font, both low-risk and mechanically similar to work already done in Phase 1 (the logo already went through an identical PNG-to-LVGL-C-array pipeline via `tools/convert_logo.py`); and (2) **five self-contained game engines plus one new cross-cutting progression system**, which is the actual bulk of the phase's complexity and risk.

For the games, none of the five algorithms are novel research problems — Sudoku generation-by-backtracking-with-uniqueness-check, Klondike's stack-of-cards model, Wordle's two-pass duplicate-letter feedback, crossword grid/numbering, and Connections' word-to-category mapping are all well-documented, decades-old (or, for Wordle/Connections, thoroughly reverse-engineered) patterns. The real engineering work is: (a) fitting each into this project's existing conventions (synchronous Storage/Content API, no dynamic allocation, cache-once screen pattern, `ratimos_app_shell_create()` chrome), and (b) sourcing/authoring Portuguese-language content for Termo, Cruzadinha, and Conexo — a real Brazilian Wordle clone (**Termo**, at term.ooo, built by Fernando Serboncini) already exists with an open **word list repository (`fserb/pt-br`)** that can very plausibly be adapted directly for this project's own Termo implementation, which meaningfully de-risks that game's content problem. Crossword and Connections content have no equivalent pre-built PT-BR source and must be hand-authored by the developer as small, compiled-in puzzle sets (consistent with this being a one-off personal gift, not a content platform).

The progression system is the one piece with no existing project precedent and the most design freedom. Prior art from Duolingo (streak-as-loss-aversion) and "garden growth" mobile mechanics (Two Dots-style) converges on a simple, implementable pattern: **one shared numeric counter + a small number of discrete milestone stages**, each stage mapped to a swapped static image asset (not a continuously-animated meter) — this fits LVGL's image-widget model perfectly and needs no new rendering capability. This research proposes a concrete default (N=~20-30 daily completions across 5-6 visual stages, plus 5 game-exclusive decorative unlocks, one per game) as a discretionary starting point for the planner/user to confirm, not a locked number.

The other cross-cutting problem this phase must solve for the first time is **write-persistence**: every existing Storage/Content API domain (`letters.c`, `photos.c`, `tracks.c`, `games.c`, `settings.c`) is read-only, either serving compiled constants or reading fixture files once at boot. Per-game progress and the shared garden/castle meter must be **written** back to disk and survive a full simulator relaunch (not just in-session navigation) — this is new territory for the codebase and should be treated as its own tracer task before the 5 games are built on top of it.

**Primary recommendation:** Build a small `ratimos_storage_get_game_state()`/`ratimos_storage_save_game_state()` pair (D-10) backed by one fixed-size binary state file per save-slot under a new gitignored `assets/save/` directory (mirroring `assets/mock/`'s dev-only convention), get that single read/write/reload round-trip proven and unit-tested first, then build the 5 games and the progression counter on top of it — in that order, as separate plans/waves.

### Pattern 1: Cache-once screen + per-game state struct

**What:** Every game screen follows the existing `s_jogos_screen`/`build_jogos_screen()` static-pointer pattern (build once, `lv_screen_load()` on every subsequent visit) — but each game additionally owns an in-memory state struct that is (a) mutated during play, (b) written to the new storage domain on every meaningful state change (not just on navigate-away, to survive an unexpected quit), and (c) loaded once when the screen is first built.
**When to use:** Every one of the 5 game screens.
**Example:**
```c
/* Source: mirrors src/ratimos/apps/jogos_app.c's existing s_jogos_screen pattern */
static lv_obj_t * s_sudoku_screen = NULL;
static ratimos_sudoku_state_t s_state; /* loaded once, mutated in place */

static lv_obj_t * build_sudoku_screen(void)
{
    ratimos_storage_get_game_state(RATIMOS_GAME_SUDOKU, &s_state, sizeof(s_state));
    ratimos_app_shell_t shell = ratimos_app_shell_create("sudoku", "toque numero");
    /* ... render s_state.board into a 9x9 grid ... */
    return shell.screen;
}

void ratimos_sudoku_show(lv_event_t * e)
{
    (void) e;
    if (!s_sudoku_screen) s_sudoku_screen = build_sudoku_screen();
    lv_screen_load(s_sudoku_screen);
}

/* called from every cell-tap handler after mutating s_state.board[...] */
static void on_cell_changed(void)
{
    ratimos_storage_save_game_state(RATIMOS_GAME_SUDOKU, &s_state, sizeof(s_state));
}
```

### Pattern 2: Date-seeded daily puzzle

**What:** Daily-mode puzzles are generated deterministically from a seed derived from the current calendar date (e.g. days-since-epoch), so the same day always produces the same puzzle without needing network access or a bundled per-day table.
**When to use:** Sudoku daily mode; optionally Termo/Conexo if the developer wants a rotating daily word/category set instead of static content.
**Example:**
```c
/* Source: general PRNG-seeding pattern, confirmed via WebSearch as the
 * standard technique behind Wordle-style daily puzzles (not vendor-specific
 * code -- Wordle's actual seed derivation is not open-source) */
uint32_t days_since_epoch = (uint32_t)(unix_time / 86400);
srand(days_since_epoch);
/* proceed with the same randomized-backtracking generator used for
 * non-daily puzzles, now fully deterministic for that calendar day */
```
**Caveat:** `native_sim` has no RTC yet (that lands in Phase 4) — for this phase, "today's date" must come from the host PC's system clock (`time(NULL)`), which is a reasonable stand-in but should be flagged as a temporary source until Phase 4's real RTC is wired in.

### Anti-Patterns to Avoid

- **Directory-scanning content discovery for game puzzles/word lists:** This project has an established V12-style discipline (per `letters.c`/`photos.c` comments) of never using `dirent.h`/directory scanning for content — always a fixed, hardcoded manifest or compiled-in array. Apply the same discipline to crossword/connections content: a compiled `const` array of puzzle structs, not a runtime directory scan of a `puzzles/` folder.
- **Continuous/animated progression meters:** Don't build a smoothly-animating garden that grows pixel-by-pixel with every point — prior art (Two Dots, Duolingo) and this project's asset-pipeline reality (hand-authored pixel art, not procedural rendering) both point to a small number of **discrete milestone images**, swapped via `lv_image_set_src()`, not a custom-drawn continuous animation.
- **Dynamic allocation in save/load paths:** `content_api.h`'s own header comment states the whole API is "sem alocacao dinamica" (no dynamic allocation) — game state structs must be fixed-size (e.g. `char board[9][9]`, not a `malloc`'d variable-length structure), consistent with every existing domain.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Pixel font rasterization to LVGL bitmap format | A custom bitmap-font renderer | `lv_font_conv` (official LVGL tool) | Purpose-built, handles bpp/kerning/Unicode-range selection correctly; this project already delegates the equivalent image problem to a script (`convert_logo.py`) rather than hand-writing a PNG decoder |
| Sudoku "is this puzzle uniquely solvable" check | A custom heuristic guess | A counting backtracking solver (stop early at 2 solutions found) | This is the one non-negotiable correctness requirement for sudoku generation — an ad-hoc check risks shipping unsolvable or multi-solution puzzles, which is a much worse gift-experience bug than a slow generator |
| Card game legal-move validation (Klondike) | Freeform drag-and-drop with no rule engine | An explicit move-validation function per move type (tableau-to-tableau, tableau-to-foundation, stock-to-waste) | Cards silently accepting illegal moves is a common, hard-to-debug solitaire clone bug; centralizing legality checks in one function per move type makes it testable via Unity like `test_storage.c` |
| Wordle duplicate-letter feedback | A naive single-pass color-per-letter loop | The standard 2-pass (greens-then-yellows-with-decrementing-counter) algorithm | A single-pass implementation is the single most common Wordle-clone bug (over-crediting duplicate letters) — well-documented failure mode across every source found |

**Key insight:** Every game in this phase has a decades-old-to-several-years-old, well-documented reference algorithm. The risk in this phase is not "can this be solved" but "does the developer correctly implement the known-tricky edge case per game" (sudoku uniqueness, klondike legal-move enforcement, wordle duplicate letters) — plan verification steps around these specific edge cases, not just "does the game render."

## Common Pitfalls

### Pitfall 1: Read-only Storage API pattern doesn't cover write-back

**What goes wrong:** All 5 existing Storage/Content API domains (`letters.c`, `photos.c`, `tracks.c`, `games.c`, `settings.c`) are read-only — they read fixtures/constants once at splash-time and only ever return copies. A naive extension of this pattern for game state would silently fail to persist across a simulator relaunch, satisfying JOGOS-02 (navigate-away-and-back within a session) but silently failing PROGRESSAO-01 and the "survives sessions" clause of JOGOS-02's own success criterion.
**Why it happens:** Every existing precedent in this codebase is read-only; it's easy to copy the `list_letters()`-style pattern (memcpy from a static cache) without adding the write-through-to-disk step the new domain actually needs.
**How to avoid:** Design `ratimos_storage_save_game_state()` to `fopen(path, "wb")`/`fwrite()` a fixed-size struct immediately (not just update the in-memory cache), and prove the full write-then-relaunch-then-read round trip with a Unity test before building any game UI on top of it.
**Warning signs:** A UAT check that only tests "navigate away and back" (single session) instead of "quit the simulator process and relaunch" will falsely pass an in-memory-only implementation.

### Pitfall 2: `assets/save/` accidentally committed or accidentally read as mock content

**What goes wrong:** This project's fixture convention (`assets/mock/`) is deliberately git-tracked, read-only, generic placeholder content (D-14/D-15 from Phase 1). A new runtime-written save directory needs the opposite treatment (gitignored, per-developer-machine, potentially containing "real" play progress) — conflating the two conventions risks either committing a developer's personal save file to the public repo, or a hardcoded fixture accidentally overwriting real save data.
**Why it happens:** `assets/` currently has exactly one convention (`mock/`); a second, differently-governed subdirectory under the same parent is easy to blur.
**How to avoid:** Add `assets/save/` to `.gitignore` explicitly in the same task that creates the directory; name it distinctly from `mock/` in both path and in-code comments (mirror the existing D-15 "the name makes it unambiguous this is dev-only" reasoning).
**Warning signs:** `git status` showing an unexpected `assets/save/*.bin` as untracked-but-not-ignored after first game-state write.

### Pitfall 3: `lv_table`/`lv_buttonmatrix` touch targets too small on a 320x480 panel

**What goes wrong:** A 9x9 sudoku grid or a 5x5+ crossword grid, rendered at full screen width (~300px content area per `app_shell.c`'s `RATIMOS_SCREEN_W` minus padding), gives each cell roughly 30-35px or less — workable for a mouse cursor in `native_sim` but potentially too small for a real fingertip once Phase 3 hardware lands (though that verification is explicitly out of this phase's scope per the ROADMAP note).
**Why it happens:** LVGL's default table/buttonmatrix cell sizing is proportional (divides available width evenly), not touch-target-aware by default.
**How to avoid:** Explicitly size cells against this project's locked spacing scale (D-16: 4/6/8/10/16/24px) — favor fewer, larger cells where content allows (e.g. a 5-letter Termo row of tiles has much more per-cell room than a 9x9 sudoku grid), and note in the plan that final touch-target confirmation is deferred to Phase 3's stylus verification per the ROADMAP's explicit scope note.
**Warning signs:** Visually cramped grids in the `native_sim` screenshot/UAT step even with a precise mouse cursor.

### Pitfall 4: Sudoku "difficulty" implemented as clue-count only

**What goes wrong:** A common naive shortcut is "easy = 40 clues, medium = 30, hard = 20" — this does not reliably correlate with actual human-perceived difficulty (a 30-clue puzzle solvable by pure elimination can feel easier than a 35-clue puzzle requiring advanced techniques).
**Why it happens:** Clue-count is the simplest number to control during generation; solving-technique-based difficulty scoring requires implementing/checking for specific techniques.
**How to avoid:** For a v1 personal-gift scope, clue-count-based difficulty tiers are an acceptable, honest simplification — just document it as a known simplification rather than presenting it as true difficulty grading, and pick clue-count bands wide enough to feel distinct (e.g. easy ~40-45, medium ~30-35, hard ~22-27).
**Warning signs:** N/A — this is a scope/expectations pitfall, not a bug; flag explicitly in the plan so it isn't silently treated as "solved difficulty grading."

## Code Examples

### Wordle-style feedback (2-pass duplicate-safe algorithm)

```c
/* Source: general algorithm pattern confirmed via WebSearch (multiple
 * independent Wordle-clone writeups); not vendor code -- adapt directly. */
typedef enum { FEEDBACK_ABSENT, FEEDBACK_PRESENT, FEEDBACK_CORRECT } letter_feedback_t;

void termo_score_guess(const char guess[5], const char answer[5], letter_feedback_t out[5])
{
    int counts[26] = {0};
    for (int i = 0; i < 5; i++) counts[answer[i] - 'a']++;

    for (int i = 0; i < 5; i++) out[i] = FEEDBACK_ABSENT;

    /* Pass 1: exact matches first, consuming from the letter tally */
    for (int i = 0; i < 5; i++) {
        if (guess[i] == answer[i]) {
            out[i] = FEEDBACK_CORRECT;
            counts[guess[i] - 'a']--;
        }
    }

    /* Pass 2: remaining letters, only while tally > 0 */
    for (int i = 0; i < 5; i++) {
        if (out[i] == FEEDBACK_CORRECT) continue;
        int idx = guess[i] - 'a';
        if (counts[idx] > 0) {
            out[i] = FEEDBACK_PRESENT;
            counts[idx]--;
        }
    }
}
```

### Sudoku uniqueness check (counting solver, stop at 2)

```c
/* Source: standard "counting backtracking solver" pattern confirmed via
 * WebSearch across multiple sudoku-generator writeups; adapt for this
 * project's board representation. */
static int count_solutions(int board[9][9], int limit)
{
    int r, c;
    if (!find_empty_cell(board, &r, &c)) return 1; /* one full solution found */

    int total = 0;
    for (int digit = 1; digit <= 9 && total < limit; digit++) {
        if (is_valid_placement(board, r, c, digit)) {
            board[r][c] = digit;
            total += count_solutions(board, limit - total);
            board[r][c] = 0;
        }
    }
    return total;
}

/* A puzzle is uniquely solvable iff count_solutions(board, 2) == 1 */
```

## Garden/Castle Progression System — Concrete Proposal (D-03/D-04/D-05/D-06)

This is the phase's one genuinely novel design surface; prior art review (Duolingo streaks, Two Dots-style garden growth — see Sources) converges on a pattern that is buildable with zero new rendering capability:

**Proposed data model** (fits directly into the D-10 Storage/Content API extension):

```c
typedef struct {
    uint16_t shared_completions;         /* increments on ANY game's daily-mode win */
    uint8_t  game_exclusive_unlocked[5]; /* bitmask/bool per game: sudoku, paciencia,
                                             termo, cruzadinha, conexo -- true once
                                             that game's daily mode has been won >=1 time */
} ratimos_progression_state_t;
```

**Proposed milestone mapping** (A3, needs user confirmation — not locked):
- `shared_completions` maps to one of ~5-6 discrete milestone images (e.g. bare castle grounds -> foundation walls -> walls + first garden bed -> towers + blooming garden -> flag raised + full garden -> "complete" state with both castle and garden fully rendered), swapped via `lv_image_set_src()` exactly like the splash logo swap, at even thresholds (e.g. every 4-6 completions) up to a top end-state around 20-30 total completions.
- Each `game_exclusive_unlocked[i]` maps to one small decorative sprite (a specific flower type or castle ornament) composited onto the same scene once that game has been won in daily mode at least once — giving each of the 5 games a small, permanent, game-specific mark on the shared visual without a second progression tree.

**Why this shape:** It satisfies D-05's two-part requirement (shared meter + per-game exclusive items) with exactly two fields, needs no new LVGL capability beyond image-swapping already proven by the splash/logo pipeline, and keeps the asset budget small enough for a solo hobbyist with no animation tooling (a handful of static pixel-art scene images, not a sprite-animation system).

**What must be persisted:** Both fields above, via the same `ratimos_storage_save_game_state()`-family API proposed for per-game state (Pitfall 1) — this is exactly why the persistence tracer task should land before individual games are built, since the progression counter is written from inside every game's win-condition code path.
