  <name>Task 1: Storage API gains a cheap saved-state probe</name>

  <read_first>
    - `src/storage/content_api.h` — the game-state API surface added in plan 02.1-01, and the header's no-dynamic-allocation contract comment
    - `src/storage/game_state.c` — the fixed save-path table, the record header layout, and the validate-on-load path this probe must not duplicate
    - `test/test_storage_game_state/test_storage_game_state.c` — the suite being extended
    - `src/ratimos/apps/jogos_app.c` — the launcher that will call the probe once per row on every build
  </read_first>

  <files>src/storage/content_api.h, src/storage/game_state.c, test/test_storage_game_state/test_storage_game_state.c</files>

  <behavior>
    - `ratimos_storage_has_game_state(RATIMOS_GAME_SUDOKU)` is false when no save file exists.
    - It is true immediately after a successful save for that game.
    - It is false again after `ratimos_storage_clear_game_state()` for that game.
    - It is false for a zero-byte file, which is treated as absent rather than invalid.
    - It is false for a blob that fails validation, so a corrupted save never advertises itself as resumable progress.
    - It returns false for an out-of-range game kind without touching the filesystem.
    - `ratimos_storage_get_game_state()` also returns `RATIMOS_GAME_STATE_ABSENT`, not `_INVALID`, for a zero-byte file, so a failed write starts a clean game with no error message.
  </behavior>

  <action>
    The launcher needs to know, cheaply and per game, whether resumable progress exists. Reading and
    validating a full 512-byte blob five times on every launcher build is wasteful and would make the
    launcher depend on each game's serialization; a dedicated probe keeps that knowledge inside the
    storage domain where it belongs.

    Add `bool ratimos_storage_has_game_state(ratimos_game_kind_t game);` to `content_api.h`, declared
    next to the existing game-state functions with a doc comment stating it answers "is there
    resumable progress" and that a corrupted or empty save answers no.

    Implement it in `game_state.c` by reusing the existing validation helper rather than writing a
    second, divergent check: bounds-check the game kind, then attempt the same load the getter
    performs and return true only for the OK status. Factor the shared work into one internal helper
    if the getter does not already expose one — there must be exactly one validation implementation in
    this file, so the probe and the getter can never disagree.

    While in the load path, make the zero-byte case explicit: a file that exists but holds zero bytes
    is `RATIMOS_GAME_STATE_ABSENT`, not `_INVALID`. A zero-byte file is the natural residue of a
    failed or interrupted create, and treating it as corruption would show the player a load-failure
    message for something that never held progress. Any other size mismatch stays `_INVALID`.

    Extend `test/test_storage_game_state/test_storage_game_state.c` with one test per bullet in
    `<behavior>`, including creating a zero-byte file at the fixed save path directly from the test.
  </action>

  <verify>
    <automated>pio test -e native_sim -f test_storage_game_state &amp;&amp; pio run -e native_sim</automated>
  </verify>

  <acceptance_criteria>

  </acceptance_criteria>
