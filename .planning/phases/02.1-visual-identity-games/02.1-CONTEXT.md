**Gathered:** 2026-08-28
**Status:** Ready for planning

<domain>
## Phase Boundary

RatimOS's own visual identity (icon set + typography — color palette was already locked in Phase 1 per D-17) plus a full suite of playable games (Sudoku, Paciência/Klondike, Termo, Cruzadinha, Conexo) and a persistent daily-completion reward system (garden-inside-a-castle progression), all built and fully tested in the `native_sdl` PC simulator using mouse-as-touch input. No physical hardware is required for anything in this phase; final real finger/stylus confirmation for these games rides on Phase 3's existing passive-stylus verification once the board arrives.

**Scope note:** This phase started as "2 simple board/card games" per the original ROADMAP entry, but was explicitly expanded by the user during this discussion to 5 games + a new gamification/progression system (see Decisions below). REQUIREMENTS.md and ROADMAP.md were updated accordingly (new IDs JOGOS-03, JOGOS-04, JOGOS-05, PROGRESSAO-01). The user acknowledged this needs proportionally more research and planning than a typical phase.

<decisions>
## Implementation Decisions

### Which games ship in this phase
- **D-01:** Five games ship in this phase, not the original 2: **Sudoku** (9x9, 3 difficulty levels, daily mode with infinitely-generated or progressive puzzles), **Paciência** (Klondike variant specifically), **Termo** (Wordle-style word-guessing with per-letter correctness feedback), **Cruzadinha** (a real crossword — grid of intersecting words, each with a numbered clue, not a simplified hangman-style guess), and **Conexo** (NYT Connections-style: group 16 words into 4 hidden thematic categories). — **Reversibility:** costly — this significantly resizes the phase; descoping any of these after research/planning starts means redoing requirement traceability and phase success criteria again.
- **D-01a (resolved post-research):** Termo ships as the **real term.ooo 3-mode family**, confirmed via research: **Termo** (1 word, 6 tries), **Dueto** (2 words simultaneously, 7 tries), **Quarteto** (4 words simultaneously, 9 tries) — there is no "3-word" mode in the original game and the user chose to follow the real modes exactly rather than invent a custom escalation. All 3 modes are daily-mode only (no free-play/unlimited mode), deterministically seeded by date. Game-state model: one shared guess input applied to all unsolved boards at once per Dordle/Quordle precedent (Round 2 research), each board's win state tracked independently.
- **D-01b (resolved post-research):** Termo's PT-BR word source is **`fserb/pt-br`** (MIT-licensed, verified directly — 327★, real/maintained repo), a ~145k-entry raw lexicon that needs curation (5-letter, common-enough words) before use as the daily-answer pool — not a ready-made daily list as-is. Fallback if further curation proves difficult: VeroBP/LibreOffice hunspell pt-BR dictionary (LGPL/MPL). No live term.ooo API exists — word lists are vendored/compiled into the device, consistent with this being an offline-first device.
- **D-02:** The `car jam` placeholder title (currently compiled into `src/storage/games.c`'s static title list) is a Rush-Hour-style sliding-block traffic puzzle concept. It is explicitly OUT of this phase — kept only as a v2 backlog idea, not built now, and should be removed from the compiled placeholder list when this phase touches `games.c` (or replaced with the 5 real titles).

### Progression / reward system (new capability, needs research)
- **D-03:** The reward's visual concept is a **garden inside the castle grounds** — the user wants these two ideas (jardim + castelo) combined into one visual, not built as separate competing concepts. Exact art direction (how the castle and garden coexist visually on a 320x480 screen) is open — flagged for the phase-researcher/planner to explore concrete layout options.
- **D-04:** Progression is **fixed with a defined end-state** (e.g., N days of daily-mode completions = the garden/castle reaches "complete") — not an infinite/unbounded meter. Exact N and exact milestone-to-visual mapping are Claude's discretion / research-and-propose territory.
- **D-05:** Progress toward the shared end-state is **shared across all games' daily modes** — completing ANY game's daily challenge advances the same overall garden/castle. On top of that shared meter, there are **game-specific exclusive unlockable decorative items** (e.g. a specific flower type, a specific castle decoration) that can only be earned by completing that specific game's daily mode — giving each game its own small collectible identity without a fully separate per-game progression tree. Exact mapping of which item comes from which game is Claude's discretion.
- **D-06:** This whole progression system is a genuinely new capability the user flagged herself as needing "muita pesquisa" (a lot of research) — the phase-researcher should treat this as a first-class research topic (prior art: mobile daily-puzzle apps with streak/garden rewards, e.g. Duolingo-style streaks, "Two Dots" garden growth, etc.), not something to improvise straight into a plan.
- **D-06a (resolved post-research):** The user explicitly wants this to be **scalable/extensible, not hardcoded to one fixed ~30-day arc** — future updates should be able to extend the castle into a larger "kingdom" via content packs (e.g. a pack that adds another month of progress). The progression manifest must therefore be a **versioned, additive-safe data structure** (string `asset_id` keys, not a hardcoded enum; a generously-sized stage array so future stages append without invalidating already-earned progress on existing devices), conceptually compatible with — though not wired into, in this phase — Phase 2's existing `content_items`/`sync_client.h` cloud content-delivery pipeline, so a later phase can deliver new progression packs through the same channel instead of inventing a second one. Confirmed target for THIS phase: ~30 days / 5-6 discrete visual stages, shipped as the first version of this extensible manifest.

### Content sourcing — Cruzadinha & Conexo (resolved post-research)
- **D-11:** No usable ready-made PT-BR content or API exists for either Cruzadinha or Conexo (confirmed via dedicated research — only proprietary live products exist, e.g. Conexo Jogo, Dicio's Conexões; English NYT Connections archives are useful only for confirming the standard data shape, never as content, due to copyright). Both games ship with **small, hand-authored puzzle sets** (5-10 puzzles each) built on a **scalable, non-repeating, hand-authorable content format** (a data file — JSON or compiled C array — that a human can keep adding puzzles to over time without code changes; the new Storage/Content API game-state domain, D-10, tracks recently-used puzzle indices so the device doesn't repeat puzzles back-to-back).
- **D-12:** For Cruzadinha's clue text specifically, `ioxua/dicionario-aberto` (a PT-BR dictionary-with-definitions dataset, CC BY-SA 2.5 PT, verified via direct fetch) may be used as a starting point/seed for clue authoring. The user explicitly accepted the CC BY-SA share-alike implication for this personal, non-distributed gift device — if the codebase is ever made public, only the derived clue-content portion would need equivalent attribution/license, not the whole project. A language-agnostic crossword grid-generation algorithm (backtracking/CSP over a word+clue list) may be used to automate grid layout, but clue authoring itself remains manual work regardless of tooling.

### Visual identity — icons
- **D-07:** Icon style direction is **pixel-art, 16-bit-style, matching the official logo's (`logo/RatimOS.png`) treatment** — replacing the current single-letter text badges (e.g. "J" for jogos) used throughout `row_list.c`/`ratimos_row_create()`. The exact production method is intentionally left open: the user wants to **research existing repos/tools/fonts for generating pixel-art icons and iterate/test candidates** before locking a specific toolchain or asset pipeline — this is phase-researcher territory, not a decision to make now.

### Visual identity — typography
- **D-08:** Screen/section **titles** get a pixel-art/bitmap retro font (matching the logo's 16-bit aesthetic); **body text** (row subtitles, game instructions, crossword clues, letters, etc.) stays on the current default LVGL Montserrat bitmap font for legibility on the small 320x480 panel. This is a two-tier typography decision, not a single global font swap. — **Reversibility:** reversible — font swaps are a `lv_conf.h`/style-object change, not an architectural one.

### Module architecture
- **D-09:** Each game gets its own file pair under a new `src/ratimos/apps/jogos/` subdirectory (e.g. `jogos/sudoku.c`/`.h`, `jogos/paciencia.c`/`.h`, `jogos/termo.c`/`.h`, `jogos/cruzadinha.c`/`.h`, `jogos/conexo.c`/`.h`), each owning its own logic/UI. The existing `jogos_app.c` becomes the menu/launcher that opens each game screen — mirroring Phase 1's established per-concern directory convention (`src/board/`, `src/storage/`, `src/sync/`).
- **D-10:** Per-game in-progress state AND the shared garden/castle progression state are persisted through a **new domain added to the existing Storage/Content API** (e.g. `ratimos_storage_get_game_state()` / `ratimos_storage_save_game_state()`, extending `src/storage/games.c`) — continuing the project's established rule that app code never touches storage directly, only through the shared API. This directly satisfies JOGOS-02 and PROGRESSAO-01's persistence requirement; the existing in-memory "build-once screen cache" pattern (used for splash/cartas/jogos menu) is NOT sufficient on its own since it doesn't survive a reboot. — **Reversibility:** costly — downstream phases (and the eventual real NVS/SD-backed storage in later hardware phases) will build on whatever shape this new domain's API takes.

### Claude's Discretion
- Exact pixel-art icon production toolchain/asset pipeline (D-07) — research first, propose options, test candidates with the user.
- Exact garden-inside-castle art direction and stage-by-stage visual layout on the 320x480 screen (D-03/D-06a) — research first, propose a concrete plan; the ~30-day/5-6-stage target and extensible manifest shape are locked (D-06a), only the actual pixel art/layout is open.
- Exact mapping of which exclusive decorative item unlocks from which game (D-05).
- Sudoku puzzle generation approach (procedural infinite generator vs. a bundled set of progressive pre-made puzzles) — the user described both "gerados aleatoriamente infinitamente" and "fases progressivas" as options without picking one; research and recommend based on what's feasible on-device (this phase runs in `native_sdl` now, but the generator will eventually run on the ESP32-S3, so on-device feasibility matters even though this phase itself has no hardware constraint).
- Exact `fserb/pt-br` lexicon curation approach for Termo's 5-letter word pool (D-01b) — filtering a 145k raw word list down to a sensible common-word daily-answer set is implementation detail.
- Exact crossword grid-generation algorithm choice and exact initial puzzle/clue content within the 5-10 puzzle set (D-11/D-12).
- Exact Conexo word-group content within the 5-10 puzzle set (D-11).
