# Phase 02.1 Plan 04: Sudoku engine + screen Summary

**Fully playable 9x9 sudoku (3 difficulty bands + deterministic daily mode) with a counting-solver uniqueness guarantee proven over 20 generations per difficulty, an LVGL Grid board with per-cell 3x3 divider styling, and daily-win castle credit guarded against double-counting.**

## Performance

- **Duration:** ~40 min
- **Completed:** 2026-09-09

- **Files modified:** 6 (5 created, 1 modified)

## Accomplishments

- `src/ratimos/apps/jogos/sudoku_engine.c/.h`: pure C, LVGL-free sudoku engine — row/column/3x3-box validity check, a counting backtracking solver that stops at a caller-supplied limit (the non-negotiable uniqueness proof, never a heuristic), a local xorshift32-seeded generator with clue-count difficulty bands (facil 40-45, medio/diario 30-35, dificil 22-27), and deterministic date-seeded daily generation.
- `src/ratimos/apps/jogos/sudoku.c/.h`: cache-once sudoku screen mirroring conexo.c's shape — 4-pill difficulty/daily selector with destructive-confirm on mode switch mid-game, a 9x9 LVGL Grid board (32x32px cells, 3x3 dividers via per-cell border width/color, no extra objects), a 10-key digit keypad, and a generation-failure fallback (copy + retry pill, no board) that never hangs the event loop.
- Win state: `resolvido!` Display-tier banner on solve; daily-mode wins credit the shared castle counter exactly once via a persisted `daily_win_recorded` guard, with `+1 no castelo` shown only after a successful credit. `novo jogo` (always available) clears only the saved board, never the shared progression.
- `jogos_app.c`: sudoku's launcher row now opens `ratimos_sudoku_show` (second of five games wired, after conexo).
- 20 Unity tests in `test_jogos_sudoku`, including the load-bearing 20-consecutive-generations-per-difficulty uniqueness check, a tiny-retry-budget no-hang test, a win-from-own-solution test, and a game-state-blob round-trip test. Full suite: 79 tests, 76 pass (the 3 pre-existing `test_sync_integration` failures are environment-secret-gated and unrelated to this plan, confirmed via `git stash` on a clean checkout).

## Decisions Made

- Restored save fields (`mode`, every `given`/`filled` digit) are range-checked on load; any out-of-range value is treated as `RATIMOS_GAME_STATE_INVALID` (discard-and-regenerate) rather than clamped in place — simpler than partial clamping and structurally guarantees an out-of-range value never reaches rendering or generation (T-02.1-02/T-02.1-12).
- `novo jogo` always opens the destructive-confirm dialog regardless of board progress (it is an explicit, deliberate action); switching difficulty only confirms when the player has unsaved progress on the current board — matches the plan's independent wording for each action.
- Win-credit and win-banner logic lives inline in `sudoku.c`'s keypad callback (screen-level), rather than as a separate LVGL-free engine function like conexo's `record_win_if_needed` — Task 3's action text specifies this shape explicitly for sudoku, and the guard (`daily_win_recorded`) is still fully unit-testable via the state-blob round-trip test since it's a plain persisted field.
- Comments describing the "never use the libc global PRNG" discipline were reworded to avoid the literal substrings `rand(`/`srand(` once they were found to self-defeat the plan's own forbidden-pattern acceptance grep — see Deviations below.
