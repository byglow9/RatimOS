# Phase 1 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Platform note:** RatimOS is an embedded LVGL 9.5 / PlatformIO-native project (C, SDL2 simulator), not a web/React stack. The shadcn initialization gate does not apply — there is no `components.json`/npm design-system tooling in this repo, and none is planned. This UI-SPEC adapts the standard GSD template's intent (spacing/typography/color/copy contracts) to the project's existing hand-rolled LVGL theme layer (`src/ratimos/theme.c/.h`), which was already established in the Phase 0 baseline and is confirmed here rather than re-invented.

**Primary visual anchor:** on the home screen, the 5 section tiles (jogos/musica/album/cartas/config) draw the eye first via panel fill + accent-colored round letter-badge; the topbar (brand wordmark) and bottombar (back hint) are secondary chrome that frame the tiles but never compete with them for attention.

**Palette source (D-17, supersedes prior placeholder palette):** every color value in this UI-SPEC is now sampled directly from `logo/RatimOS.png` (the official RatimOS wordmark, 1536×1024px, pixel-level sampled — see methodology note in the Color section). This replaces the Phase-0 placeholder indigo/teal palette (`#14102b` bg / `#2b2358`+`#4a3f8f` panels / `#6dd6c4` accent) project-wide — home, splash, and all 5 app screens — not just the splash's new logo image. Per D-17, this palette rework was pulled forward from Phase 9 (VISUAL-01) into Phase 1 at the user's explicit request, now that a real brand asset exists to derive from.

## Design System

| Property | Value |
|----------|-------|
| Tool | none (custom embedded theme layer, not a package-based design system) |
| Preset | not applicable |
| Component library | LVGL 9.5.0 core widgets, wrapped by this project's own themed helpers: `ratimos_panel_create()`, `ratimos_badge_create()`, `ratimos_row_create()` (row_list.c), and the shared chrome in `app_shell.c`/`status_bar.c` (topbar/sectionbar/content/bottombar) |
| Icon library | LVGL built-in symbol font (`LV_SYMBOL_HOME`, `LV_SYMBOL_LEFT`, `LV_SYMBOL_OK`, `LV_SYMBOL_BATTERY_FULL`, etc.) — no bespoke icon set yet. A custom icon set is explicitly VISUAL-01 / Phase 9 scope, not Phase 1. |
| Font | LVGL bundled Montserrat, compiled sizes 14/20/28 only (`lv_conf.h:27-30`); `LV_FONT_DEFAULT = &lv_font_montserrat_14`. Single visual weight per size — no bold face is compiled in. |
| Image assets | New this phase — `logo/RatimOS.png` (source: 1536×1024, 8-bit RGB, pixel-art wordmark) is converted via LVGL's image tool (`LVGLImage.py`, bundled with LVGL 9.5, or the web tool at lvgl.io/tools/image-converter) into a compiled-in `lv_image_dsc_t` C array, displayed with `lv_image_create()` + `lv_image_set_src()` (LVGL v9 API — not the legacy v8 `lv_img_*` names). No other screen uses a bitmap image asset this phase; every other screen remains pure LVGL-drawn widgets/labels per the existing theme layer. |

**Splash image asset pipeline (new, this phase):** the splash screen renders the actual logo artwork, not a text recreation (per D-17's explicit instruction) — this is the one departure from "everything is hand-drawn LVGL widgets" in this project. Constraints:
- **Export format:** same color depth as `lv_conf.h`'s configured `LV_COLOR_DEPTH 16` (RGB565 / "True color", no alpha channel) — the logo's background (`#000000`) exactly matches `RATIMOS_COLOR_BG`, so no alpha-blended edges are needed; opaque RGB565 avoids a runtime color-format conversion cost on both the SDL2 simulator and the eventual ST7796 panel.
- **Compiled in, not loaded from `assets/mock/`:** the splash's fade-in (D-01) fires before the Storage API's mount/index steps (D-03) even begin, so the logo image must be resident in flash as a linked C array — it cannot depend on a successful disk/fixture read the way `assets/mock/` content does.
- **Recommended display size:** scale proportionally from the 1536×1024 source (3:2 aspect ratio) to **~256×171px**, centered horizontally on the 320px-wide splash screen (32px margin each side) — preserves the source aspect ratio exactly (no stretch/squash); leaves the existing 16px (`xl`) logo-to-bar gap and 24px (`2xl`) top/bottom margins (declared in Spacing Scale below) intact above/below the image. The executor may adjust final px dimensions within this ratio constraint if the converted asset's flash footprint needs tuning, but must not stretch the artwork off-ratio.

## Spacing Scale

**Approved locked exception — D-16 (`01-CONTEXT.md`):** this project's Phase-0 baseline already established a **2px-multiple micro-scale** (4/6/8/10) rather than the standard 4/8/16/24/32/48/64 8-point scale, because the physical target is a 320×480 3.5" panel where 8px increments consume proportionally more of the available width than on a desktop/mobile web canvas. This is not an inline spec-writer rationalization — it is logged as **D-16, a project-level locked decision** in `01-CONTEXT.md`, overriding the generic GSD 8-point-scale default for this project going forward. Phase 1 preserves this convention unchanged for all existing shell/app code, and the new splash screen follows the same scale for consistency. Larger tokens (16/24) are reserved for the few genuinely major layout breaks (splash logo-to-bar gap, screen-edge content padding).

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Badge-to-label gaps, tile internal row gaps (`tile_create` pad_row) |
| sm | 6px | Sectionbar icon-to-title gap, topbar right-cluster column gap |
| md | 8px | Panel/card internal padding (`ratimos_panel_create`), album grid column gap, splash bar-to-percentage-label gap |
| lg | 10px | Screen-edge content padding (`shell.content`/home `content` pad_all), row-list column gap, content flex pad_row |
| xl | 16px | Splash logo-to-loading-bar vertical gap (new, this phase) |
| 2xl | 24px | Splash screen top/bottom margin (new, this phase) — matches existing bar heights (22-26px) so the splash reads as "one more screen," not a visually distinct interstitial |

Exceptions: touch-target sizing (e.g. the 44px minimum tap target guideline) is **not** enforced in Phase 1 — the simulator uses SDL2 mouse input (`lv_sdl_mouse_create`), and exact touch-target px minimums only become safety-critical once the real FT6336 capacitive panel is calibrated in Phase 3 (INPUT-01/INPUT-02). Existing badge size (28×28px) and bar heights (22-26px) are below the eventual 44px guideline and should be revisited in Phase 3 planning, not blocked on here.

## Typography

LVGL's bundled Montserrat is a **bitmap/vector font family with exactly one visual weight per compiled size** — there is no bold face available without shipping a second font asset (flash-cost tradeoff, out of scope for Phase 1). Hierarchy in this project is therefore built from **size + color** (`RATIMOS_COLOR_TEXT` vs `RATIMOS_COLOR_TEXT_MUTED` vs `RATIMOS_COLOR_ACCENT`), not weight. Where the standard template asks for "2 weights," read this project's equivalent as "2 color tiers" (primary text vs muted text) layered on top of 3 fixed sizes.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Label (badges, topbar brand, bottombar hints) | 14px (`lv_font_montserrat_14`, project default) | regular (only weight compiled) | 1.2 (LVGL built-in font metric, not independently configurable per-label) |
| Body (row titles/subtitles, list items, empty-state copy) | 14px | regular | 1.2 |
| Heading (section-bar title, splash wordmark support text) | 20px (`lv_font_montserrat_20`) | regular | 1.2 |
| Display (splash logo/wordmark) | 28px (`lv_font_montserrat_28`) | regular | 1.2 |

Color-as-hierarchy substitute:
- Primary text: `RATIMOS_COLOR_TEXT` (`#f5f2f8`) — row titles, active labels. **Not** used for the splash wordmark anymore — the splash now renders the actual `logo/RatimOS.png` artwork as a compiled image asset (see Design System) rather than a styled text label.
- Muted text: `RATIMOS_COLOR_TEXT_MUTED` (`#a997ba`) — subtitles, bottombar hints, empty-state body copy, splash step captions (if used).
- Accent text: `RATIMOS_COLOR_ACCENT` (`#e6010f`) — brand wordmark in the topbar, back-button label, section-bar checkmark — see Color section below for the full reserved-for list. **Caveat:** contrast against `BG` (`#000000`) is 4.38:1 and against `PANEL` (`#2a123f`) is 3.48:1 — both meet WCAG AA for large text/icons (≥3:1: checkmark icon, back-arrow glyph, badge letter) but sit under the 4.5:1 threshold for small/regular body text on either surface. This is the real ceiling of the brightest red sampled anywhere in the source logo, not an arbitrary shortfall. Accent color is already reserved for short labels/icons only, never body-length copy, so this confirms existing scope rather than surfacing a new problem — flag for a future Phase 9 visual-identity pass if higher-contrast accent-text legibility becomes a priority.

## Color

**Superseded this phase (D-17):** every hex value below is newly derived from `logo/RatimOS.png` (pixel-sampled directly from the source PNG — see methodology note below), replacing the Phase-0 placeholder palette (`#14102b` bg / `#2b2358`+`#4a3f8f` panels / `#6dd6c4` teal-mint accent) that this same UI-SPEC previously locked. Applied project-wide — home, splash, and all 5 app screens — not just the splash's new logo image.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#000000` (`RATIMOS_COLOR_BG`) | Screen background on every screen (home, splash, all 5 apps) — sampled directly from the logo's own canvas (pure black across 1,069,011 of the source PNG's 1,572,864 pixels — the dominant color of the source asset itself). |
| Secondary (30%) | `#2a123f` (`RATIMOS_COLOR_PANEL`), `#4e2277` (`RATIMOS_COLOR_PANEL_ACTIVE`) | Topbar/sectionbar/bottombar bar fills, panel/card/row/tile backgrounds; `_ACTIVE` variant reserved for pressed/active tile state (still not wired to a pressed style in Phase 0/1 code — same pre-existing gap as before, just recolored). Both derived from the wordmark gradient's violet stop (sampled ≈ `#450194`, hue 268°), darkened to 16%/30% lightness respectively so panels read as "near-black, same world as the background" rather than a competing color block. |
| Accent (10%) | `#e6010f` (`RATIMOS_COLOR_ACCENT`) | Reserved for: topbar brand wordmark text, section-bar checkmark icon (`LV_SYMBOL_OK`), bottombar back-button label/arrow, badge circle fill (the round letter-badge used in tiles/rows — badge letter drawn in `RATIMOS_COLOR_TEXT` on this fill, contrast 4.33:1, large-glyph pass), and the splash screen's loading-bar fill. Sampled from the rook/tower mark's brightest red facet — this sits at (within 1-2 units of) the single brightest saturated-red pixel cluster anywhere in the source image, not an arbitrarily brightened value. |
| Destructive | none defined | Unchanged from the prior palette's decision — no destructive actions exist in Phase 1 scope (read-only navigation + browsing mock content). Deferred to whichever future phase introduces delete/reset actions (candidates: Phase 6 settings reset, Phase 9 game-state reset) — do not invent a destructive color token speculatively now. If one is ever needed, the logo's dark maroon bevel-shadow tone (sampled ≈ `#7f010a`) is a natural, already-on-brand candidate — noted for future reference only, not adopted as a token this phase. |

**Sampling methodology (for traceability):** `logo/RatimOS.png` (1536×1024, 8-bit RGB) was read pixel-by-pixel and clustered by hue/lightness. Four real clusters emerged: near-black background (`~#000000`, the dominant cluster), a violet gradient-top stop (`~#450194`), a bright rook red (`~#e6010f`), and an orange gradient-bottom stop (`~#fd5501`), plus a dark maroon bevel-shadow tone (`~#7f010a`). `BG` and `ACCENT` use sampled values directly (no adjustment). `PANEL`/`PANEL_ACTIVE` reuse the violet cluster's hue (268°) at lower/higher lightness (16%/30%) purpose-built for UI surface elevation, since the raw sampled violet is too bright/saturated to serve as a background fill without competing with `ACCENT`. `TEXT`/`TEXT_MUTED` (below) are likewise hue-matched to the violet cluster rather than sampled directly, since no near-white or muted-gray pixels exist anywhere in the source artwork.

**Text-hierarchy colors (supplementing the dominant/secondary/accent triad):**

| Token | Value | Usage |
|-------|-------|-------|
| `RATIMOS_COLOR_TEXT` | `#f5f2f8` | Primary text — row titles, active labels, general body copy. Near-white with a faint cool-violet tint (hue-matched to the logo's violet gradient stop, lifted to 96% lightness for legibility). Contrast vs `BG`: 18.94:1. Contrast vs `PANEL`: 15.07:1. |
| `RATIMOS_COLOR_TEXT_MUTED` | `#a997ba` | Muted text — subtitles, bottombar hints, empty-state body copy. Same violet hue, desaturated and mid-lightened. Contrast vs `BG`: 7.82:1. Contrast vs `PANEL`: 6.22:1. |

Both clear WCAG AA's 4.5:1 body-text threshold with wide margin, including against the darker `PANEL` surface — verified numerically, not eyeballed.

**Caveat for the checker — hairline borders (inherited, recolored):** every `ratimos_panel_create()`-based surface (panels, rows, tiles) currently draws a **1px accent-colored border** in addition to the reservations above. This is a pre-existing Phase-0 pattern applied broadly, which on paper looks like it violates "accent reserved for specific elements only." It is intentionally preserved here (not redesigned in Phase 1, which is a plumbing phase, not a visual-identity phase — that's Phase 9/VISUAL-01), now simply recolored from the old teal (`#6dd6c4`) to the new rook red (`#e6010f`), and flagged explicitly so the checker treats it as a **known, accepted exception** rather than a silent violation: the border is a 1px hairline (minimal perceptual area at 16-bit color depth on a 320×480 panel), not a fill, so it does not meaningfully compete with the accent's true 10%-of-visual-weight budget.

**Caveat for the checker — panel/background contrast is intentionally low:** `PANEL` (`#2a123f`) against `BG` (`#000000`) has a WCAG contrast ratio of only 1.26:1 — far below any text-legibility threshold, but this is a surface-vs-surface pairing, not a text pairing. This mirrors the logo's own true near-black canvas (D-17's stated rationale for adopting this palette at all) and is an intentional stylistic choice, not an oversight. Surface boundaries remain legible in practice via the accent-colored 1px hairline border every panel/row/tile already draws (see above). If a future visual QA pass finds panels genuinely hard to distinguish from the background in the simulator, the fix is to lean on `PANEL_ACTIVE` for more static surfaces or nudge `PANEL`'s lightness up slightly — not to abandon the near-black identity the logo establishes.

Accent reserved for (explicit list — do not expand without a Phase 9 visual-identity pass): brand wordmark (topbar, short text only — see Typography caveat on the 4.38:1/3.48:1 contrast ratios), section-bar checkmark icon, back-button, round letter-badges, splash loading-bar fill, [accepted exception] panel/row/tile 1px hairline borders (inherited, recolored not new).

**Logo reference colors (not adopted as standalone UI tokens):** the wordmark's own vertical gradient — violet `~#450194` at top to orange `~#fd5501` at bottom — exists only inside the compiled logo image asset itself (see Design System's image pipeline note) and is not recreated as a flat color anywhere else in the UI this phase. Do not introduce a "gradient purple" or "gradient orange" token into any other screen's flat-color styling without a deliberate Phase 9 visual-identity decision — current scope is: the logo's exact pixels render once, on the splash, as an image; every other screen uses the three flat tokens above (`BG`/`PANEL`/`ACCENT`) plus the two text tokens.

No per-screen loading state exists or is needed this phase. |
| populated | cartas/musica/jogos/config lists, album grid (`list-collection`) | ✅ covered | Happy path is 3-4 items per domain (D-13), rendered via the existing `ratimos_row_create()`/tile patterns — already proven to handle >1 item visually (jogos already renders 3 static rows today). |
| nav | Home screen 5 section tiles (`nav`) | ✅ covered | Section labels are fixed, short, known strings (jogos/musica/album/cartas/config) — no truncation/long-text risk. |
| overflow / long-text | Row titles/subtitles (`ratimos_row_create`), album tile labels (`list-collection`) | ⚠ unresolved | `row_list.c` and the album/home tile labels do not currently set an `lv_label` long-mode (no `LV_LABEL_LONG_MODE_DOT`/`WRAP`). Planner should add explicit long-mode truncation (recommend `LV_LABEL_LONG_MODE_DOT`) to title/subtitle labels in `row_list.c` and photo-tile labels in `album_app.c`. |
| zero-one-many | Track/photo/letter/game counts in row subtitles (e.g. "0 faixas") (`list-collection`) | ⚠ unresolved | Portuguese distinguishes singular/plural ("1 faixa" vs "2 faixas"); the current hardcoded "0 faixas" string doesn't branch on count. | partial | letter/track/game fixtures with a missing title field (`list-collection`) | ⚠ unresolved | Fixtures are hardcoded/manifest-driven per Pitfall 4, so a missing title is a developer authoring error, not a real runtime path — but the Storage API's list functions should still return a safe default label (e.g. "sem titulo") rather than an empty/garbage string if a fixture field is blank, as cheap defensive coding. Not blocking for Phase 1. |
| error | Splash storage-init step failure (missing/malformed fixture file) (`interactive-control`) | 🧪 backstop | See Copywriting Contract's optional error-state copy. Recommended default exists but is not wired/tested this phase; if the planner does add a fallback path, it should be covered by a held-out test in `test/test_storage/` (e.g. "list function returns 0 gracefully on a missing manifest entry, does not crash") rather than assumed to silently pass. |
| overflow | Splash logo image at ~256×171px (`static-content`) | dismissed | The scaled `logo/RatimOS.png` image (see Design System's image pipeline note) comfortably fits within the 320px screen width with 32px margins each side, and the declared 24px top/bottom margins; it is a fixed compiled-in image asset, not dynamic/user-controlled content, so wrapping/truncation/clipping risk is zero by construction. |
