## Summary

This phase has two genuinely separate halves that must both be provably correct from a PC, with zero ESP32 hardware involved: (1) a Supabase Postgres schema + two Edge Functions implementing an opaque-bearer-token auth model, and (2) a small, reusable C HTTPS client living in `src/sync/` that exercises that backend from the `native_sim` PlatformIO environment established in Phase 1. Both halves are already tightly scoped by CONTEXT.md's locked decisions (D-01 through D-13) — this research fills in the concrete syntax, current API shapes, and pitfall list needed to plan them without guessing.

On the backend: Supabase Edge Functions run on Deno, are written in TypeScript, and are created/deployed with the `supabase` CLI (`supabase functions new`, `supabase functions deploy`, local dev via `supabase start` + `supabase functions serve`). Because this project's device auth is a custom opaque bearer token (never a Supabase-issued JWT), **both Edge Functions must be deployed with `verify_jwt = false`** in `supabase/config.toml` — otherwise Supabase's platform-level API gateway rejects every device request with its own 401 before the function code ever runs, which would produce a false pass on this phase's "401 rejection" success criterion for the wrong reason. Token hashing (SHA-256, not bcrypt — bcrypt is for low-entropy human passwords, not high-entropy random tokens) uses Deno's built-in Web Crypto API, no external hashing library needed. RLS on `devices`/`content_items`/`ota_releases` is genuinely simple to get right here: enabling RLS with **zero policies** for `anon`/`authenticated` is Postgres's documented default-deny behavior, and since D-09 already routes all real traffic through the service-role-privileged Edge Functions (which bypass RLS entirely), a deny-all RLS posture is the correct, simplest implementation of "defense-in-depth against a direct PostgREST call using the publishable key" — no custom per-device session variable or claims-mapping function is needed.

On the client: `libcurl` is confirmed as the right choice for D-05 — it is already present as a runtime library on this dev machine, is the de facto standard HTTP/TLS client for C, defaults to verifying the peer certificate against the system CA bundle on Linux/macOS (Windows needs an explicit CA bundle path), and its `CURLOPT_HTTPHEADER`/`curl_slist` API is exactly what's needed to attach a `Authorization: Bearer <token>` header. One real gap surfaced by this research: this project's existing `native_sim` environment compiles as pure C (`-std=gnu11`), but CLAUDE.md's project-wide JSON library recommendation, ArduinoJson, is a **C++-only** library — it cannot compile in this environment. This phase's JSON parsing (for the "what's new" response body) needs a pure-C alternative; `cJSON` (DaveGamble/cJSON, MIT, 13k GitHub stars, ANSI C89, current release v1.7.19) is the standard, widely-used fit and is flagged here as a deliberate, documented deviation from CLAUDE.md's ArduinoJson recommendation for this specific module only.

**Primary recommendation:** Build the Edge Functions in TypeScript/Deno with `verify_jwt = false` and SHA-256 token hashing via Web Crypto; enable RLS with no policies on all three tables as the defense-in-depth backstop; implement `src/sync/` as a `board.h`-style abstraction (`sync_http_*` contract) with a `libcurl`-backed `native_sim` implementation and `cJSON` for response parsing, mirroring Phase 1's board/HAL split pattern exactly.

### Pattern 1: Board/HAL-style HTTP abstraction (mirrors Phase 1's `board.h`)
**What:** A tiny header (`http_client.h`) declaring the HTTP contract the rest of `src/sync/` calls; only one implementation is linked per PlatformIO environment (`native_curl` today, an ESP32 `HTTPClient` implementation added and swapped in via `build_src_filter` in Phase 7 — exactly how `board.h`/`native_sdl`/`waveshare_s3_35` already work in this repo).
**When to use:** Any time device code needs to talk HTTPS, so Phase 7 changes one file, not every call site.
**Example:**
```c
/* src/sync/http/http_client.h */
#ifndef RATIMOS_SYNC_HTTP_CLIENT_H
#define RATIMOS_SYNC_HTTP_CLIENT_H
#include <stddef.h>

typedef struct {
    int status_code;      /* 0 if the transport itself failed (no response) */
    char body[4096];       /* fixed-size, allocation-free, matches Storage API convention */
    size_t body_len;
} ratimos_http_response_t;

/* Performs an HTTPS GET with an optional bearer token. url MUST be https://.
 * Returns 0 on transport success (response populated regardless of status_code),
 * non-zero if the transport itself could not complete the request. */
int ratimos_sync_http_get(const char *url, const char *bearer_token,
                           ratimos_http_response_t *out);

#endif
```
```c
/* src/sync/http/native_curl/http_client.c (excerpt) — Source: curl.se/libcurl/c/httpcustomheader.html */
#include <curl/curl.h>
#include <string.h>
#include "../http_client.h"

static size_t write_cb(char *ptr, size_t size, size_t nmemb, void *userdata) {
    ratimos_http_response_t *resp = (ratimos_http_response_t *)userdata;
    size_t n = size * nmemb;
    if (resp->body_len + n >= sizeof(resp->body)) n = sizeof(resp->body) - resp->body_len - 1;
    memcpy(resp->body + resp->body_len, ptr, n);
    resp->body_len += n;
    resp->body[resp->body_len] = '\0';
    return size * nmemb; /* tell curl the full chunk was "handled" even if truncated */
}

int ratimos_sync_http_get(const char *url, const char *bearer_token, ratimos_http_response_t *out) {
    memset(out, 0, sizeof(*out));
    CURL *curl = curl_easy_init();
    if (!curl) return -1;

    struct curl_slist *headers = NULL;
    if (bearer_token) {
        char auth_header[512];
        snprintf(auth_header, sizeof(auth_header), "Authorization: Bearer %s", bearer_token);
        headers = curl_slist_append(headers, auth_header);
    }

    curl_easy_setopt(curl, CURLOPT_URL, url);               /* must be https:// — SEC-02 */
    curl_easy_setopt(curl, CURLOPT_SSL_VERIFYPEER, 1L);       /* default is already 1L; explicit for auditability */
    curl_easy_setopt(curl, CURLOPT_SSL_VERIFYHOST, 2L);
    curl_easy_setopt(curl, CURLOPT_HTTPHEADER, headers);
    curl_easy_setopt(curl, CURLOPT_WRITEFUNCTION, write_cb);
    curl_easy_setopt(curl, CURLOPT_WRITEDATA, out);

    CURLcode res = curl_easy_perform(curl);
    if (res == CURLE_OK) {
        long code;
        curl_easy_getinfo(curl, CURLINFO_RESPONSE_CODE, &code);
        out->status_code = (int)code;
    }
    curl_slist_free_all(headers);
    curl_easy_cleanup(curl);
    return (res == CURLE_OK) ? 0 : -1;
}
```

### Pattern 2: `verify_jwt = false` + manual bearer-token validation in Edge Functions
**What:** Because this project's device token is opaque (D-08), not a Supabase-issued JWT, both `register-device` and `whats-new` must disable Supabase's platform-level JWT gateway check and do their own validation inside the handler.
**When to use:** Any Edge Function whose caller is not a Supabase-Auth-authenticated user/browser session.
**Example:**
```toml
# supabase/config.toml
[functions.register-device]
verify_jwt = false

[functions.whats-new]
verify_jwt = false
```
```typescript
// supabase/functions/whats-new/index.ts
// Source: supabase.com/docs/guides/functions/auth-headers, supabase.com/docs/guides/functions/secrets (patterns cross-referenced this session)
import { createClient } from "npm:@supabase/supabase-js@2";

async function sha256Hex(input: string): Promise<string> {
  const data = new TextEncoder().encode(input);
  const digest = await crypto.subtle.digest("SHA-256", data);
  return Array.from(new Uint8Array(digest)).map(b => b.toString(16).padStart(2, "0")).join("");
}

Deno.serve(async (req) => {
  const authHeader = req.headers.get("Authorization");
  if (!authHeader?.startsWith("Bearer ")) {
    return new Response(JSON.stringify({ error: "missing bearer token" }), { status: 401 });
  }
  const token = authHeader.slice("Bearer ".length);
  const tokenHash = await sha256Hex(token);

  // SUPABASE_URL / SUPABASE_SERVICE_ROLE_KEY are auto-injected by the platform —
  // do not set these manually as Edge Function secrets.
  const admin = createClient(
    Deno.env.get("SUPABASE_URL")!,
    Deno.env.get("SUPABASE_SERVICE_ROLE_KEY")!
  );

  const { data: device, error: deviceErr } = await admin
    .from("devices")
    .select("id")
    .eq("token_hash", tokenHash)
    .maybeSingle();

  if (deviceErr || !device) {
    return new Response(JSON.stringify({ error: "invalid token" }), { status: 401 });
  }

  const { data: items, error: itemsErr } = await admin
    .from("content_items")
    .select("id, title, type, content_date, url")
    .eq("device_id", device.id)
    .is("delivered_at", null);

  if (itemsErr) {
    return new Response(JSON.stringify({ error: "query failed" }), { status: 500 });
  }
  return new Response(JSON.stringify({ items }), { status: 200, headers: { "Content-Type": "application/json" } });
});
```

### Pattern 3: RLS "locked-but-empty" default-deny as the defense-in-depth backstop
**What:** Enable RLS on every table (already forced by D-02's project setting) and add **no** policies for `anon`/`authenticated`. Postgres denies all access to those roles by default once RLS is on; only the `service_role` (used exclusively inside Edge Functions, per D-09) bypasses RLS entirely [CITED: supabase.com/docs/guides/database/postgres/row-level-security — "when RLS is enabled with no policies... Postgres... denies everyone by default (except the table owner and roles that bypass RLS, like service_role)"].
**When to use:** Exactly this phase's situation — no table should ever be reachable by a raw client holding only the publishable key, because the Edge Functions are the sole intended access path.
**Example:**
```sql
-- supabase/migrations/<timestamp>_phase2_schema.sql (excerpt)
create table devices (
  id uuid primary key default gen_random_uuid(),
  token_hash text not null unique,
  label text,
  created_at timestamptz not null default now(),
  last_seen_at timestamptz
);
alter table devices enable row level security;
-- Intentionally NO policies for anon/authenticated below this line: RLS default-deny
-- is the entire defense-in-depth mechanism (D-09). Only service_role (used inside
-- Edge Functions) can read/write this table. Do not add a permissive policy here.

create table content_items (
  id uuid primary key default gen_random_uuid(),
  device_id uuid not null references devices(id) on delete cascade,
  title text not null,
  type text not null check (type in ('letter', 'photo', 'music')),
  content_date date not null default current_date,
  url text,
  delivered_at timestamptz,
  created_at timestamptz not null default now()
);
alter table content_items enable row level security;

create table ota_releases (
  id uuid primary key default gen_random_uuid(),
  version text not null,
  url text,
  released_at timestamptz
);
alter table ota_releases enable row level security;
```

### Anti-Patterns to Avoid

- **Leaving `verify_jwt` at its default (`true`) on these functions:** every device request will get a 401 from Supabase's own gateway, before your handler code runs — this will masquerade as your own auth logic "working" when it's actually never being reached. Explicitly set `verify_jwt = false` and validate the opaque token manually.
- **Writing a real per-device RLS policy that parses `request.headers` to extract and hash the bearer token inside Postgres:** technically possible (via `current_setting('request.headers', true)`), but this duplicates the Edge Function's own validation logic in a second language/layer for a project that explicitly routes all real traffic through the Edge Function anyway (D-09). Adds real complexity for a benefit this project doesn't need.
- **Storing the plaintext token anywhere in Postgres, even in a column named for auditing/debugging:** hash before insert, always — see Security Domain below.
- **Hardcoding the Supabase project URL/keys as string literals inside `src/sync/*.c`:** D-03 requires reading from `.env`; even though the publishable key and project URL are "safe to reference" per D-01, treat them as project configuration data read at runtime/build-time, not compiled-in literals, so a future device-token or project rotation doesn't require a firmware rebuild+re-flash of files unrelated to the actual change.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|--------------|-----|
| SHA-256 hashing of tokens | A custom C or TypeScript SHA-256 implementation | Deno's built-in `crypto.subtle.digest("SHA-256", ...)` (Edge Function side); no hashing needed on the C client side at all — it only ever sends the plaintext token over TLS | Web Crypto's SHA-256 is a one-line, standard-library call; a hand-rolled hash function is a correctness and security risk for zero benefit |
| JSON parsing | A hand-written ad-hoc string-scanning JSON parser in `src/sync/sync_client.c` | `cJSON` (see Standard Stack) | JSON parsing edge cases (escaping, numbers, nesting) are exactly the kind of "looks simple, isn't" problem a mature single-purpose library solves once |
| TLS/certificate verification | Any custom socket+OpenSSL wrapper | `libcurl`'s built-in `CURLOPT_SSL_VERIFYPEER`/`CURLOPT_SSL_VERIFYHOST` (already correct by default) | Hand-rolled TLS handling is one of the most common sources of real-world security vulnerabilities (accepting invalid certs, wrong hostname checks); libcurl's defaults are already correct — the only work needed is *not disabling* them |
| Random opaque token generation | A custom PRNG-based token generator | Deno's `crypto.randomUUID()` or `crypto.getRandomValues()` inside the `register-device` function | Cryptographically-secure randomness is a solved, standard-library problem; a hand-rolled generator risks insufficient entropy |

**Key insight:** every "don't hand-roll" item in this phase already has a zero-additional-dependency standard-library or single well-established-library answer (Web Crypto, cJSON, libcurl's own TLS defaults) — there is no good reason to write custom code for any of these four problems in this phase.

## Common Pitfalls

### Pitfall 1: ArduinoJson (CLAUDE.md's stack-wide JSON pick) cannot compile in `native_sim`
**What goes wrong:** A planner or executor reflexively reaches for ArduinoJson (CLAUDE.md's documented project-wide JSON library) to parse the "what's new" response, then discovers it's a C++-only, Arduino-framework-dependent library that will not compile under `native_sim`'s current `-std=gnu11` pure-C build (`platformio.ini`, `[env:native_sim]`, `build_flags = -std=gnu11 ...`).
**Why it happens:** CLAUDE.md's stack table was written project-wide, before this specific `native_sim` environment's pure-C constraint (established in Phase 1) was known to interact with a C++-only library choice.
**How to avoid:** Use `cJSON` for `src/sync/` specifically (see Standard Stack/Alternatives Considered above); this is called out here explicitly as a documented deviation from CLAUDE.md, not an oversight — flag it for user confirmation during planning/discuss-phase if not already implicitly accepted.
**Warning signs:** A `pio run -e native_sim` failure citing missing `<Arduino.h>` or C++-only syntax errors (`class`, `template`, references) inside a file that's supposed to compile as plain C.

### Pitfall 2: `verify_jwt` left at its default blocks every device request at the gateway
**What goes wrong:** Both Edge Functions return 401 for *every* request, including ones with a perfectly valid opaque bearer token — the response looks like "auth is working" (it *is* 401-ing invalid requests) but it's actually rejecting valid ones too, for the wrong reason (missing/invalid Supabase JWT, not the app's own token check).
**Why it happens:** Supabase Edge Functions default to `verify_jwt = true`, and this project's tokens are intentionally not Supabase JWTs (D-08).
**How to avoid:** Set `verify_jwt = false` for both `register-device` and `whats-new` in `supabase/config.toml`, and confirm redeploys don't silently reset it (there is a known CLI issue where JWT verification settings can be ignored on function *updates* specifically — re-verify after every `supabase functions deploy` during development).
**Warning signs:** A 401 response body that doesn't match your own handler's error JSON shape (e.g., Supabase's own generic gateway error text instead of `{"error": "invalid token"}`).

### Pitfall 3: Testing the "another device's token" success criterion has no natural single-device fixture
**What goes wrong:** The roadmap's success criterion #2 says the test client "gets rejected (401)... with... another device's token," but this project has exactly one real device ever (D-12's own stated rationale) — there's no second real device to source a genuine "another device's" token from.
**Why it happens:** The roadmap's phrasing was likely written generically (as if testing multi-tenant isolation) without accounting for this project's explicit single-device scope.
**How to avoid:** Interpret and implement this as: register one disposable *test* device via `register-device` (deletable after the test run) to obtain a syntactically valid, hashed-and-stored token, then either (a) use that second test device's token against the primary test device's expectations, or (b) more simply, test with a syntactically valid but never-registered token string — both exercise the exact same code path (`token_hash` not found in `devices` → 401) and are equally valid proof of SEC-01. Document which interpretation the plan uses (see Open Questions).
**Warning signs:** A test suite that only ever tests "no token" and treats that as satisfying the full criterion — this misses the "wrong/foreign token" code path entirely, which is a different branch in the handler (missing header vs. header present but hash lookup fails).

### Pitfall 4: `pio test` and `pio run` share the same `native_sim` build output path (recurrence from Phase 1)
**What goes wrong:** Phase 1's 01-03 summary documented this exact issue: running `pio test -e native_sim` overwrites `.pio/build/native_sim/program`, so a subsequent manual run of that binary launches the last-built test binary, not the app.
**Why it happens:** Both `pio run` and `pio test` build into the same environment's shared output directory.
**How to avoid:** This applies identically to this phase's new `test/test_sync/` suite — always `pio run -e native_sim` (rebuild the real app) immediately before any manual/checkpoint demo, after running tests.
**Warning signs:** A "smoke test" that unexpectedly prints Unity test output instead of launching the LVGL app.

### Pitfall 5: Integration tests against the real Supabase project require network access and a pre-existing test token
**What goes wrong:** `pio test -e native_sim -f test_sync` (or however the suite is filtered) silently hangs or fails with a generic curl transport error if run offline, or if `.env` doesn't yet contain a valid test device token (which must be minted via a manual `register-device` call before the test suite can pass) — this is a different failure mode than a logic bug and can be misdiagnosed as one.
**Why it happens:** Success criterion #4 explicitly requires verification "against the real Supabase project from a PC-native build" — this is an integration test by nature, not a pure unit test, and depends on the same manual bootstrap step (D-06's "called manually during testing") as a test precondition.
**How to avoid:** Split `test/test_sync/` into a pure-logic unit suite (JSON parsing, no network) and a clearly-separated integration suite that documents its precondition (a `.env`-provided test token) at the top of the file; don't fold both into one Unity `RUN_TEST` block indistinguishably.
**Warning signs:** CI or a fresh clone failing this phase's tests with no clear indication that a manual registration step was ever required first.

### Pitfall 6: libcurl's default TLS behavior differs across OSes, especially on a from-source Windows build
**What goes wrong:** On Linux/macOS, libcurl defaults to trusting the system CA bundle and "just works" for a real Supabase HTTPS endpoint (a well-known public CA). On Windows, libcurl does not automatically discover a system CA bundle, and a missing/misconfigured `CURLOPT_CAINFO` produces `SSL certificate problem: unable to get local issuer certificate` [CITED: multiple cross-referenced sources this session — see Sources].
**Why it happens:** libcurl's CA-bundle auto-discovery is a Linux/macOS/BSD behavior, not a Windows one.
**How to avoid:** If any contributor develops on Windows, document that a `cacert.pem` bundle path may need to be set via `CURLOPT_CAINFO`; do not "fix" this by disabling `CURLOPT_SSL_VERIFYPEER` (that defeats SEC-02's entire purpose).
**Warning signs:** The exact same code working on the primary dev machine (confirmed Linux, per this research) but failing with a TLS error on a different OS/CI runner.

## Open Questions

1. **Should `src/sync/` include a compiling-but-unlinked ESP32 stub, mirroring Phase 1's `waveshare_s3_35/board.c`?**
   - What we know: D-04/D-05 only require the abstraction interface to exist and the `libcurl`/`native_sim` implementation to be real; Phase 1 established a parallel pattern (a stub for the not-yet-available hardware, excluded from the link via `build_src_filter`) for `board.h`.
   - What's unclear: whether this phase should proactively add an empty `esp32/http_client.c` stub now (for structural parity, consistency, and to prove the abstraction is genuinely swappable) or leave that entirely to Phase 7.
   - Recommendation: follow Phase 1's precedent and add the stub now — it's low-cost and directly demonstrates D-05's "swap implementation, not call sites" goal is actually achievable, the same way Phase 1 did for `board.h`.

2. **Does the "what's new" endpoint mark `delivered_at` on read, or is that a separate, later action?**
   - What we know: D-12 defines `delivered_at` as nullable, "null = still pending." The roadmap's success criterion #4 only requires the endpoint to *return* pending items, not to define exactly when they transition to delivered.
   - What's unclear: whether marking-as-delivered happens automatically on this endpoint's read (simplest, but means a failed client-side write after a successful read could "lose" content) or requires a separate acknowledgment call (more correct, but is that a Phase 2 or Phase 7 concern, since Phase 7 is where the device actually writes synced content to local storage?).
   - Recommendation: leave `delivered_at`-setting logic out of this phase's `whats-new` endpoint entirely (read-only, returns all `delivered_at IS NULL` rows every time) — Phase 7, which actually persists synced content locally, is the natural, correct place to decide when to mark delivery, once local write success can be confirmed. Flag this explicitly in the plan so Phase 7's research doesn't have to rediscover it.

3. **Exact currently-injected Edge Function environment variable name for the service-role-equivalent secret.**
   - What we know: multiple 2026-era sources agree `SUPABASE_SERVICE_ROLE_KEY` is still auto-injected and functional inside Edge Functions even after the new `sb_publishable_`/`sb_secret_` key rollout.
   - What's unclear: Supabase's key-system migration is an actively evolving area (legacy key deprecation is scheduled for end of 2026); the exact variable name should be re-confirmed against the live project's Edge Function environment (e.g., via a one-line debug log during first local `functions serve` run) rather than assumed from this research alone.
   - Recommendation: the plan's first Edge Function task should include a quick `console.log(Object.keys(Deno.env.toObject()))`-style sanity check (removed before the final commit) to confirm the actual injected variable names for this specific project, rather than trusting this document's name unconditionally.

## Security Domain

### Applicable ASVS Categories

| ASVS Category | Applies | Standard Control |
|----------------|---------|---------------------|
| V2 Authentication | yes | Opaque per-device bearer token (D-08), hashed at rest with SHA-256, validated inside the Edge Function against `devices.token_hash` |
| V3 Session Management | no | Stateless bearer-token model, no server-side session state; token revocation is "delete the row," not a session invalidation mechanism |
| V4 Access Control | yes | Application-level `device_id` scoping inside the Edge Function (primary), RLS default-deny (secondary/defense-in-depth) per D-09 |
| V5 Input Validation | yes | Edge Function validates the `Authorization` header shape (`Bearer <token>`) before use; Postgres `check (type in ('letter','photo','music'))` constraint validates `content_items.type` at the schema level |
| V6 Cryptography | yes | SHA-256 via Deno's built-in Web Crypto API for token hashing — never hand-roll (see Don't Hand-Roll) |
| V9 Communications | yes | HTTPS/TLS only (SEC-02) — Supabase's Edge Function/API endpoints are HTTPS-only by platform default; the C client must never construct an `http://` URL (libcurl's `CURLOPT_SSL_VERIFYPEER`/`VERIFYHOST` left at their secure defaults, never disabled) |

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|------------------------|
| Admin secret (D-07) leaked via git history, logs, or chat | Elevation of Privilege | Store only as a Supabase Edge Function secret (`supabase secrets set`) and in the gitignored `.env` (D-03); never log the header value in the Edge Function |
| Opaque device token leaked via logs/error messages | Information Disclosure | Never log the raw `Authorization` header or token value inside the Edge Function; only log the hash or a truncated/redacted form if debugging is needed |
| MITM on device↔backend traffic if TLS is ever silently downgraded/disabled | Tampering, Information Disclosure | libcurl's `CURLOPT_SSL_VERIFYPEER`/`VERIFYHOST` left at secure defaults (explicit in code for auditability, per Pattern 1's example); never add a "disable cert check for testing" code path that could accidentally ship |
| Timing side-channel on token-hash lookup | Information Disclosure (theoretical) | Accepted as low-risk for this project's threat model per Assumption A5 (indexed DB equality lookup, single-device hobby project) — documented, not mitigated with custom constant-time infrastructure |
| Registration endpoint reachable without the admin secret (misconfiguration) | Elevation of Privilege | Explicit `X-Admin-Secret` check as the *first* line of the handler, returning 401 immediately if absent/mismatched, before any DB write is attempted |
| RLS accidentally left disabled on a new table (human error bypassing D-02's automatic-RLS trigger) | Elevation of Privilege / Information Disclosure | Explicit `alter table ... enable row level security;` in the migration SQL itself (Pattern 3) — don't rely solely on the invisible project-level "Enable automatic RLS" toggle; make it visible and auditable in the schema file too |
