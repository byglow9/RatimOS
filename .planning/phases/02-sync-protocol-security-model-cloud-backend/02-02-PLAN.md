<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Device (bearer token) → whats-new Edge Function | Untrusted network path; the device's own opaque token crosses here |
| whats-new Edge Function → Postgres (service-role client) | Trusted internal path, bypasses RLS by design (D-09) |
| Any direct client holding only the publishable key → content_items/ota_releases via PostgREST | Untrusted; must be denied by RLS default-deny (verified live in Plan 4) |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-2-02 | Information Disclosure | whats-new's extracted bearer token / TEST_DEVICE_TOKEN | high | mitigate | The token is only ever hashed for lookup, never logged; TEST_DEVICE_TOKEN lives only in gitignored .env. |
| T-2-04 | Information Disclosure (theoretical) | devices.token_hash lookup inside whats-new | low | accept | Same indexed-equality, single-device rationale as Plan 1 (RESEARCH.md Assumption A5). |
| T-2-06 | Elevation of Privilege / Information Disclosure | content_items/ota_releases RLS | high | mitigate | Both tables carry an explicit `enable row level security;` line with zero policies (Task 1); verified live in Plan 4 against a real anonymous PostgREST call. |
| T-2-07 | Information Disclosure | content_items query scope | high | mitigate | The query filters by `device_id = <resolved id from the hashed token>` inside the Edge Function's own code — never a client-supplied device_id parameter, so no request can ask for another device's content_items by ID. |

</threat_model>
