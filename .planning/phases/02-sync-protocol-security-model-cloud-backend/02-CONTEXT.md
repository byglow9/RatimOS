# Phase 2: Sync Protocol, Security Model & Cloud Backend - Context

**Gathered:** 2026-08-27
**Status:** Ready for planning

<domain>
## Phase Boundary

The cloud backend (Supabase Postgres schema + Auth/token model + Edge Functions) and the device-authentication protocol exist and are provably secure and testable from a PC-native build, entirely independent of ESP32 hardware. This phase covers: the `devices`/`content_items`/`ota_releases` schema with RLS, a minimal device-registration mechanism that issues per-device bearer tokens, a "what's new" metadata endpoint, and a reusable C protocol client (`src/sync/`) that exercises all of this from the `native_sim` environment. Real binary file upload/download (photos/music), BLE-based provisioning UX, and OTA firmware consumption are explicitly NOT this phase — they belong to Phases 6, 7, and 8 respectively, which will call the mechanisms built here.

</domain>

- **D-02:** Project-creation security settings: **Data API enabled**, **"Automatically expose new tables" disabled**, **"Enable automatic RLS" enabled** (Supabase's automatic-RLS event trigger forces RLS on every new table by default). This is a deliberate fail-closed default matching this phase's security goal — no table can accidentally ship without RLS. — **Reversibility:** reversible (project settings, not schema; can be changed later without migration).
- **D-03:** Credentials live in a `.env` file at the repo root, added to `.gitignore`, never committed. The C protocol client (and any Edge Function local dev tooling) reads from there. The Secret/service-role key in particular must never appear in code, commits, or chat — it is a local-only, developer-held secret.

### Protocol Client Architecture
- **D-04:** The PC-native test client for this phase is **real, reusable C code** — not a throwaway Python/Node script. It lives in a new `src/sync/` directory (sibling of `src/board/` and `src/storage/` from Phase 1), continuing that phase's per-concern directory convention, and runs inside the existing `native_sim` PlatformIO environment. — **Reversibility:** costly — choosing a scripting language instead would have meant Phase 7 rewrites the client from scratch; this decision is what makes Phase 7 a port instead of a rewrite.
- **D-05:** HTTP/TLS library choice for `native_sim` is Claude's discretion (see below) — resolve during research, behind a small abstraction interface so only the implementation swaps out (not call sites) when Phase 7 ports this to the ESP32's `HTTPClient`/`NetworkClientSecure`.

### Device Registration & Token Model
- **D-06:** Device registration for this phase's testing uses a **minimal registration endpoint** (a Supabase Edge Function, e.g. `POST /devices`) that inserts a `devices` row and returns a fresh token — called manually (curl/script) during testing. This is explicitly the same mechanism Phase 6's BLE provisioning flow will invoke later; only the BLE transport is out of scope here, not the registration logic itself.
- **D-07:** The registration endpoint is **protected by an admin secret** (not open to anonymous callers) — only the developer can mint a new device token, even during this testing phase. — **Reversibility:** reversible (an application-level check, not a schema/contract change).
- **D-08:** The device token itself is an **opaque random string** (e.g. UUID/32+ random bytes), stored (hashed) in `devices.token` — not a signed JWT. Rationale: trivial to generate/validate in C on the ESP32 later with no JWT library dependency, and trivially revocable by deleting/invalidating the row (vs. needing short expiries + a revocation list for JWTs).

### RLS Enforcement Model
- **D-09:** All device-facing data access goes **through Supabase Edge Functions**, which manually validate the device's opaque bearer token against the `devices` table and then query using service-role privileges, explicitly scoped by `device_id` in code. Postgres **RLS policies are still defined on every table** (satisfying the roadmap's literal "RLS policies scoping each device to only its own data" success criterion) as **defense-in-depth** — so that even a raw PostgREST call using the publishable key (bypassing the Edge Functions entirely) cannot read another device's rows. The primary, intended access path for a real device is always the Edge Function, never direct table access. — **Reversibility:** costly — switching to a JWT-claim-based direct-PostgREST model later would require reissuing every device's credential and rewriting the Edge Functions into thinner passthroughs.

### Content Scope for This Phase
- **D-10:** The "what's new" endpoint returns **metadata only** this phase — `content_items` rows carry title, type (`letter`/`photo`/`music`), date, and an optional `url` field left empty/placeholder. Real binary file upload to Supabase Storage is explicitly **Phase 7 (Cloud Content Sync)** scope, already on the roadmap for it.
- **D-11:** Test/seed data for `content_items` is a **fixed SQL seed script** (3-4 fictitious items, mirroring Phase 1's fixture-count convention), run manually in Supabase's SQL editor during testing — not a second insert-endpoint.
- **D-12:** "Pending/new" tracking uses a simple nullable **`delivered_at` timestamp column directly on `content_items`** (null = still pending) — no separate device×content join table. Rationale: this project has exactly one real device ever (a personal one-off gift, not a multi-device product), so per-device delivery-state tracking via a join table would be unused complexity.

### ota_releases Table
- **D-13:** `ota_releases` exists in this phase's schema with **only its column structure** (e.g. `version`, storage path/`url`, `released_at`) and **zero rows** — no fictitious test firmware release is seeded, since Phase 8 hasn't yet decided the real shape/fields this table will need for rollback tracking etc.

### Claude's Discretion
- Exact HTTP/TLS library for the `native_sim` C client (D-05) — likely `libcurl` behind a thin abstraction, confirm during research.
- Exact `ota_releases` column list/types beyond the loosely-named fields above (`version`, `url`, `released_at`) — Phase 8 may still refine this later; keep it minimal and obviously extensible for now.
- Exact Edge Function names/routes, request/response JSON shapes for registration and "what's new" — implementation detail, not something the user needs to pre-decide.
